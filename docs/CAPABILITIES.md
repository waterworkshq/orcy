## Status convention

Rows that need a qualifier carry an explicit status label:

- **Partial** — part of the designed surface is live; the rest is deferred with the gap named.
- **Declaration-only** — validated and listed, but not callable.
- **Deprecated** — retained read-only or superseded; do not build on it.
- **Known limitation** — shipped behavior with a named, unclosed gap.

Unlabeled descriptions are current-state claims only after code verification; absence of a label does not imply authorization for every principal.

| **Hierarchical model** | Habitats → Missions → Tasks → Subtasks. Missions flow through columns on the board; tasks move through a state machine inside each mission. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Mission status derivation** | Mission status is derived automatically from the states of its child tasks. No manual status juggling. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Task lifecycle** | Tasks progress through a defined state machine: Pending → Claimed → In Progress → Submitted → Approved/Rejected → Done/Failed. Canonical lifecycle transitions are logged; the stale-sweep release now records its event atomically and enqueues `on_fail`/failure-context receipts. Agent deletion is atomic and event-owning too: held `claimed`/`in_progress` tasks are released with the full bundle (event + receipts, actor = the real operator), terminal/legacy assigned rows keep status and history and are unassigned with an `updated` audit event, inbound delegation offers are cancelled with an audit event, and assigned `submitted`/`rejected` work blocks deletion (typed 409) — all-or-nothing, never a partial teardown. Automation-rule `release_assignment` is closed the same way: it releases through the canonical release act-tx (event + receipts, system actor `automation-executor`, metered) fenced on the evaluated/pinned task epoch — a tokened task re-claimed after evaluation (even by the same agent) refuses; legacy NULL-to-NULL epochs retain the documented limitation; on the frozen delivery path the evaluated intent is pinned into the action checkpoint before execution and the release + checkpoint proof commit atomically. Plugin-context task operations are now event-owning and fenced: `taskWriter.assignTask` commits state + execution token + `claimed` event atomically through the claim authority (system actor `plugin:<pluginId>:<contributionId>`, one transition-budget meter, assignee preserved in the event metadata), `taskWriter.releaseTask(taskId)` / `releaseTask(taskId, { expectedToken: task.executionToken })` releases only an assignment whose epoch+assignee pair the same invocation observed via `taskReader.getTask` or its own claim (previously-read-or-claimed — one observed assigned pair for the one-arg form; an explicit token must select exactly one observed pair; without a selector, multiple observed pairs are ambiguous; an explicit token is ambiguous only if it matches multiple observed pairs (different tokens = a valid explicit selection); observed `null` ≠ missing; `assignTask` returns void, token via subsequent `getTask`) through the canonical release act-tx (in-tx budget + habitat + epoch + assignee fences; `released` event + receipts atomic; `plugin:<pluginId>` reason with plugin-run provenance; postlude best-effort once), and `taskWriter.updatePriority` commits the change and its `updated` event atomically (unmetered); `automationAction` contributions may declare `taskReader` as the observation source (bound to the enrolled habitat — it reads every task row there, not per-assignment restricted). Import execution-state reset is also audited: the habitat import execution-state reset (`tasks:reset`) is now event-owning: every reset task emits exactly one `updated` audit event inside the import publication transaction (actor = the human whose request actually executed the publication — on the expired-lease recovery path this can be a different authenticated importer than the attempt's original initiator, and both records keep their true principals; metadata links the import-attempt record (reservation initiator retained), mode, and the task's true pre-reset status; terminal states included), event-row only — no SSE, watchers, mission recalculation, receipts, or recovery effects fire from the marker. For the STALE-SWEEP, budget-refused candidates remain eligible for a later sweep pass if the ceiling changes and the other checks still pass; an automation run whose `release_assignment` was budget-refused is NOT automatically retried — a new authorized automation attempt (or the stale sweep, if the agent later goes stale) is required; no implicit automatic resumption exists. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Atomic claiming** | Claims run through the claim authority: one database transaction, a conditional write with typed contention outcomes — one winner, no double assignment under concurrent access from multiple orcys. | [DATABASE.md](DATABASE.md) |
| **Domain routing** | Domain matching is an eligibility filter, not a data-isolation wall: it governs the work an orcy is offered — suggestions, auto-assignment, and claim eligibility. Board, list, and task-detail surfaces can still expose sibling-domain work. | [CONFIGURATION.md](CONFIGURATION.md) |
| **Capability matching** | Capability matching works the same way as domain matching: it governs suggestions, assignment, and claim eligibility. It does not wall off read/list surfaces, which can expose sibling work. | [CONFIGURATION.md](CONFIGURATION.md) |
| **Mission dependencies** | Mission dependencies gate claiming: tasks in a mission with unmet dependencies are not claimable until the dependency resolves; claimability-aware suggestion and assignment paths respect the gate. Read and list surfaces can still show the task. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Release gates (Roadmap Activation)** | Missions can be gated behind a release type (`patch`/`minor`/`major`) or an exact version pin (`v0.25`). Gated missions block their tasks from claiming until a matching release ships; gates auto-resolve at read-time from the `releases` table. | [ARCHITECTURE.md](ARCHITECTURE.md) |

| **Dynamic Habitat Skills** | Each habitat auto-generates a living skill document from high-strength pulse signals, task outcomes, and agent observations. Signals are clustered, scored, and promoted into domain knowledge, conventions, and patterns. Agents receive skill context when claiming tasks. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Project insights** | Institutional memory — promoted signals become persistent insights tagged by relevance. Surfaced in mission context via tag matching. Outlive individual missions. | [SKILL.md](SKILL.md) |

| **WebUI Signal Board** | Tab layout on MissionDetailPage (Tasks/Pulse/Activity). 8 pulse components, habitat signal panel, insights panel. Real-time SSE updates. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Task Board View** | Table/list alternative to kanban view with sorting, filtering, bulk operations. Toggle between Board and Table views per habitat. | [ARCHITECTURE.md](ARCHITECTURE.md) |

For agents whose recorded heartbeat is older than 30 minutes, the sweep attempts release of their `currentTaskId` task subject to current owner/epoch/heartbeat and budget checks; stored task state persists; on a successful release the durable event and receipts are recorded — effect delivery uses bounded retries and may dead-letter. | [DATABASE.md](DATABASE.md) |

## Execution & Reliability

| Capability | What it does | Learn more |
|---|---|---|
| **Task publication kernel** | Task-creation origins that register post-cutover flow through one CAS-enforced one-way state machine (durable attempts across eight states) with governance interceptors, an observation gate, and lease-fenced dispatch/assignment workers; a committed task may still await observation or assignment. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Claim authority** | Single-transaction claiming with a typed refusal taxonomy: occupancy → task-intrinsic guards → observation → reservation → transition-budget gates, conditional write with version increment, post-write TOCTOU verify. | **Retry ladder** | Server-side retries **when a retry policy is configured** (per-task, else per-habitat; without one, no retries): exponential backoff with the policy defaults (60s base, ×2, 1h cap), status-filtered; human escalation on exhaustion only when the policy sets `escalateToHuman` — without it, exhaustion does not escalate. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Automation delivery core** | For frozen-revision `release.shipped` deliveries: fenced-inbox admission dedup, crash-atomic terminalization, and a completion outbox delivered after commit (the guarantee covers completion-event delivery only, not arbitrary action side effects); unproved non-resume-safe actions park as `attention_required` rather than re-execute. Live-rule runs keep the canonical lifecycle without this outbox. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Atomic scheduled occurrence reservation** | Occurrence reservation under `BEGIN IMMEDIATE` with unique occurrence identity, one-shot schedule advance, lost-race rollback, and terminal-preserving repair for rejected occurrences — reserving the occurrence atomically does not guarantee exactly-once external publication. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| **Transition budget** | A per-task meter of Execute↔Review transitions against a habitat-configured ceiling (default 21), counted from the audit trail itself. Human actors are unmetered; the first refused guarded transition at the ceiling schedules a best-effort escalation to the habitat's humans (escalation failures are logged, not durably retried — escalation is not promised). | [ARCHITECTURE.md](ARCHITECTURE.md) |

This is finite protection for these two operations — no platform-wide Task-mutation, quality-template-administration or immutable-quality-snapshot guarantee follows. The two Task effort writes (`log-effort`, `correct-effort-entry` via the task dispatch tool and `POST /tasks/:id/effort-entries` with `/:entryId/correct`) resolve the URL Task's actual Mission → Habitat before any write (missing ancestry 404; human team nonmember 403 with zero rows and zero metric mutations) and land through ancestry-contained INSERTs — the logged entry only lands while the URL Task exists, the correction only lands while the corrected entry belongs to the URL Task and that Task exists at statement-evaluation time (foreign/absent entries zero-match 404 after the preserved missing-404/foreign-400 pre-check for admitted actors), keeping the post-commit order entry → audit (throws, partial commit preserved) → Task/Mission metric recalculation → `effort.updated` SSE. This is finite row-level protection for these two writes — not universal Task-mutation protection. The two served Task evidence write actions (`correct-code-evidence-link`, `resolve-gap`) resolve the URL Task's actual Mission→Habitat before any evidence row is read (missing Task/Mission 404; human team nonmember 403 with zero rows and zero audit/SSE) and require the source link/gap to belong to that exact Task at the final SQL statement (`id AND target_type AND target_id`; zero-match 404, and the response is that statement's own RETURNING row) — so another Task's row, a Mission row whose id text matches, or a row that moved target after the pre-read is a 404 with no mutation; `replacementLinkId` remains a reference only (any existing link, no content grant), and a missing reference is an existing-FK 500 rather than a silent clear. Their Mission equivalents adopt the same exact-pair source containment as a shared-signature consequence, which adds **no** Mission membership admission. ## Release-Aware Automation (v0.24.0)

When a release is detected (GitHub `release` webhook, `workflow_run` release-workflow completion, CLI, or REST), the system classifies it by semver type and — when the global and per-habitat promotion switches are both on — reconciles the frozen activation epoch: matched deferred findings in eligible groups activate up to the per-release cap, deferred or oversized groups wait for a later Release or manual activation, and a failed projection leaves itself and later projections pending (surfaced as `incompleteProjections`) rather than being silently dropped — closing the loop between "we know about this" and "now we're working on it" without a human re-surfacing each item.
