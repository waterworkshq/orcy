# v0.37.0 — Deepen: Installation Transaction

Architecture-deepening release (candidate 10 from the 2026-07-11 review). Converts `@orcy/installer` from a descriptive append-only log into a transactional system with crash recovery. **Installer-only — no server/database changes, no breaking changes for running deployments.**

## Why

The installer recorded what it did (an append-only manifest) but owned no notion of intended state, transaction boundaries, or recovery. Concretely: writes weren't atomic, the manifest silently duplicated on re-install, an interrupted install left no recoverable state, `update` only re-ran packages + fenced markdown (leaving MCP/skills/service/env stale), and uninstall could delete files under a still-running service or lose user-modified skills. This release makes install/update/uninstall a transactional, idempotent, crash-recoverable operation.

## What changed

- **Two-file transaction model.** A transient journal (`~/.orcy/install-journal.json`; its presence signals an interrupted install) plus a committed manifest (`install-manifest.json`), both written atomically (temp + fsync + rename). `record()` is a journal-aware seam with `{path, action}` dedup and metadata upsert (hash/keys/backup/marker) — re-installs no longer grow a duplicate-laden manifest.
- **`update` replays full intent (D5).** `updateInstall` now re-applies env, service, MCP config, markdown, and skills from a typed `InstallIntent` persisted in the manifest — instead of only packages + fenced markdown. Markdown injection is remove-then-inject (idempotent across duplicate/malformed fences).
- **`doctor` / `verify` split (G10).** `doctor` stays a cron-safe liveness probe (added stale-journal WARN + service-status). New `verify` is a read-only consistency auditor (missing recorded paths, duplicate entries, stale journal; footprint dirs reported informationally, not as drift).
- **Migrate hardening + v1→v2 reconcile (B6/G11).** Legacy `~/.kanban → ~/.orcy` migration rewrites manifest paths immediately after the irreversible rename and is best-effort from there. A new `reconcile` step upgrades v1 manifests to v2 on `update` (dedup, path rewrite, version bump) — existing installs upgrade in place.
- **G2 full recovery.** A stale journal triggers viability-aware recovery: **resume** (discard + re-run; idempotency makes done steps converge), **rollback** (actively reverse done steps via the shared `reverseEntry`, including stopping a started service), or **abort**. A `--recover` flag enables CI auto-recovery (resume-if-viable, else rollback). An unresolved `registerAgent` (POST done, credential write not) blocks resume and surfaces the orphaned agent.
- **CLI hardened.** Unknown args now error instead of silently installing (`--yes --bogus` no longer installs); `--yes`/`-y`/`--recover` are recognized; the stale-journal hard-fail propagates a non-zero exit code; `@clack` cancel is treated as abort.

## Cold review + remediation

A 3-agent independent cold review (codex/GPT-5.6, non-overlapping file ownership) produced ~30 findings across four severity tiers. **All four tiers were remediated** before release: recovery-contract soundness (registerAgent orphaning, resume idempotency, rollback completeness), data-loss/correctness paths (missing-hash skill deletion, manifest-deleted-on-failure, path over-match, markdown multi-fence, sentinel order), atomic-write durability (per-write unique temp + fchmod + fd cleanup + real fsync error propagation), and CLI/UX accuracy (exit code, validate-all-args, select cancel, verify/doctor output, backup-prune glob). Each fix has a dedicated test where testable.

## Verification

- `@orcy/installer`: 129 tests pass (hermetic — real `node:fs` against a temp home; `node:child_process`/`fetch`/`@clack` mocked). Zero `packages/installer/` typecheck errors.
- No server, database, UI, MCP, or daemon changes — those packages are untouched.

## Operator action

**None.** No schema changes, no migrations, no ADRs, no breaking changes. Existing installs pick up reconcile on their next `orcy-install update`. The `--recover` flag is opt-in; without it, non-interactive runs still fail safely on a stale journal (unchanged).

## Known limitation

macOS `launchctl` service-liveness detection and the parent-directory fsync durability behavior are exercised only on Linux CI — they warrant real-platform macOS validation in a follow-up. (A false-negative on macOS `doctor` service-status is safe; the prior false-positive is fixed.)
