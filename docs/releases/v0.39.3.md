# v0.39.3 — Patch: Lost status and operator recovery for stale plugin runs

Plugin runs that crashed or were orphaned mid-execution stayed stuck in `running` forever, blocking trigger-event dedup and leaving no way for an operator to close them out.

## Lost terminal status

Adds `lost` as a new terminal status for plugin runs. A run marked `lost` is treated as durably accounted — it is included in trigger-event dedup alongside `running`, `succeeded`, and `failed`, so the system does not re-fire the same trigger after an operator clears a stuck run. This prevents duplicate side effects from crash recovery.

## Operator recovery action

New endpoint: `POST /habitats/:habitatId/plugins/runs/:id/lost`. An operator (or agent) can mark a stale `running` run as `lost`. The action enforces:

1. **Habitat ownership** — the run must belong to the specified habitat.
2. **Status guard** — only `running` runs can be marked `lost`. Terminal runs (`succeeded`, `failed`, etc.) are rejected to prevent re-classification.
3. **Staleness threshold** — the run must have been in `running` state for at least 30 minutes (configurable). A `force: true` body override skips this guard for edge cases where an operator knows the run is dead sooner.

## Verification

## No operator action required

No schema changes, no migrations. The `lost` status is additive to the existing `PluginRunStatus` union. Existing trigger-event dedup automatically accounts for `lost` runs without configuration changes.
