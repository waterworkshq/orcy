# v0.35.4 — Patch: Notification write scope + linked-identity recipient dedup

Three deferred items close cleanly. No schema changes, no migrations, no ADRs, no API contract additions.

## Fix 1 — Dedicated `notification.write` scope for ack/snooze (closes RM-5)

The `/api/shared/notifications/deliveries/:deliveryId/ack` and `/api/shared/notifications/deliveries/:deliveryId/snooze` routes were listed in the Remote MCP action manifest with `requiredScope: "read"` even though they mutate delivery state (`status = "acknowledged"` and `snoozedUntil` respectively). Every other write endpoint in the manifest has a dedicated write scope (`comment`, `claim`, `submit`, `release`, `heartbeat`, `evidence_link`, `pulse.post`); ack/snooze were the only POSTs whose manifest entry used `"read"`.

The server-side routes also lacked a `remoteActionScope(...)` preHandler — they relied solely on delivery-ownership checks. So in practice, any authenticated remote participant could ack/snooze their own notifications; the `"read"` declaration was correct-as-documented but inconsistent with the write-scope pattern.

This patch:

- Adds `"notification.write"` to the `RemoteActionScope` union (`@orcy/shared`) and to the `remoteActionScopeSchema` zod enum (`packages/api/src/routes/remoteAccess.ts`). The MCP package's local inline `requiredScope` union is extended in parallel.
- Updates `REMOTE_MCP_ACTIONS["notifications.ack"]` and `["notifications.snooze"]` to declare `requiredScope: "notification.write"`.
- Adds `remoteActionScope("notification.write")` to both routes' `preHandler` chains in `packages/api/src/routes/sharedApi.ts`, so the scope is now **enforced** (not just declared).
- Adds `"notification.write"` to both `observerActions` and `contributorActions` in `isActionAllowedForStanding` (`packages/api/src/middleware/remoteAuth.ts`) — observers and contributors both receive notifications and should both be able to ack/snooze them.
- Replaces the stale "ack/snooze is a read-adjacent write" comment in `packages/mcp/src/__tests__/remote-mcp.test.ts` with an explicit assertion that ack/snooze declare `notification.write`.
- Adds two scope-enforcement tests in `packages/api/src/test/podBridgeRemoteAuth.test.ts` (block `["read", "comment"]` from `notification.write`; allow `["notification.write"]`).

## Fix 2 — Linked-identity recipient dedup (closes RM-8)

`findRemoteRecipientsForEvent` (`packages/api/src/services/remoteNotificationResolver.ts`) deduplicated candidates by `${participantType}:${participant.id}`. When the same person/orcy appeared in two remote participant records linked via `externalIdentityId` (cross-pod identity linking via the identity provider), both records produced distinct dedup keys and BOTH got notified → duplicate delivery to the same individual.

The dedup key now uses `externalIdentityId` when present (linking the same person/orcy across pods or records), and falls back to a per-id key (`__id__:${id}`) when `externalIdentityId` is null — so unlinked participants are never accidentally merged. The first record wins; iteration order over grants and participants is unchanged.

Four new tests in `packages/api/src/test/remoteNotificationResolver.test.ts` pin the new behavior:

- Same `externalIdentityId` across two pods → one entry (first record wins).
- Different `externalIdentityId` → both returned (existing behavior pinned).
- One `externalIdentityId` and one null → both returned (null is its own bucket).
- Three participants across three pods, two sharing one `externalIdentityId` and one sharing another → two entries.

## Operator Action Required

**Add `notification.write` to remote grants that should ack/snooze notifications, then redeploy.**

This patch is the first scope enforcement on the ack/snooze routes — previously, scope was declared in the manifest but not enforced server-side. Any existing remote grant that previously relied on `read` to ack/snooze will now receive 403 `ACTION_NOT_IN_GRANT_SCOPES` unless `"notification.write"` is added to its `actionScopes` array.

For deployments without remote participants (`ORCY_REMOTE_KEY` not configured), no action is needed — the routes are not mounted.

For deployments WITH remote participants: update each affected grant via the admin surface (or `PATCH /habitats/:id/grants/:grantId` if API-only) to include `"notification.write"` in its `actionScopes`. The migration is mechanical: add one string to one JSON array per grant.

## Backward Compatibility

- The `notification.write` scope addition is additive to the type union and zod enum; existing serialization remains valid.
- The `notification.write` scope **is** a breaking change for any deployment that relies on the prior `read`-implicit behavior on ack/snooze. See Operator Action above.
- The linked-identity dedup is a one-way fix: notifications previously duplicated are now deduplicated. No data is lost; the recipient always sees exactly one delivery for any event.
