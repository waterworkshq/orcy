# v0.39.8 — Patch: Enforce signal detector manifest rate limit defaults

Plugin signal detectors declared `maxDetectionsPerMinute` and `maxSignalsPerHour` defaults in their manifests, but these limits were never enforced. A noisy or runaway detector could invoke indefinitely and flood the pulse feed with signals, consuming concurrency slots and drowning out legitimate detections.

## What changed

- **Rate limiter** (`detectorRateLimiter.ts`, new): in-memory sliding-window tracker keyed by `(habitatId, canonicalKey)`. Two windows: a 60-second window counting detector invocations against `maxDetectionsPerMinute`, and a 3600-second window counting emitted signals against `maxSignalsPerHour`. Exposes `checkAndRecordDetection`, `checkSignalHourQuota`, `recordSignalsEmitted`, and `resetDetectorRateLimits`.

- **Invocation runtime** (`invocationRuntime.ts`): after acquiring a detector concurrency slot, the runtime now evaluates `checkDetectorRateLimit` from the runtime deps. If throttled, the slot is released, the run is finished as `rate_limited` with a descriptive reason, and the detector is not invoked.

- **Plugin manager** (`pluginManager.ts`): wires the rate limiter into the runtime deps. Reads `rateLimitDefaults` from the detector's manifest contribution and applies both windows. After a successful detector run, emitted signals are recorded against the hourly quota via `recordSignalsEmitted`. State is cleared on `resetPlugins()`.

## Verification

- `@orcy/api` typecheck: clean.
- `@orcy/api` tests: 3 passed in `pluginDetectorRateLimit.test.ts`.

## No operator action required

No schema changes, no migrations. Detectors without `rateLimitDefaults` in their manifest are unaffected — the rate check passes through. The tracking is in-memory and resets on server restart.
