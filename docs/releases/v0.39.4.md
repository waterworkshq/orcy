# v0.39.4 — Patch: MCP tool schema and client interface migration to habitatId

Aligns all remaining non-habitat MCP dispatch tools with the canonical `habitatId` naming convention introduced in v0.36.0, completing the migration that was partially applied across earlier releases.

## What changed

The MCP package's dispatch tool schemas, handler contracts, and client interfaces still referenced `boardId` in several places — a legacy naming from before `habitatId` became the canonical identifier. This patch completes the migration:

- **Tool schemas**: all dispatch tools (task, mission, pulse, review, sprint, subscription, suggest, notification, automation, webhook, template, scheduled-task, audit) now use `habitatId` in their input schemas instead of `boardId`.
- **Handler contracts**: handler functions and dispatch utilities accept `habitatId` consistently.
- **Client interfaces**: the API client surface (`packages/mcp/src/api.ts`, `packages/mcp/src/api/interfaces.ts`) uses `habitatId` in method signatures and types.
- **Transparent fallback**: legacy callers passing `boardId` still work via fallback compatibility — no breaking change for external integrations.

## What stayed the same

No changes to the underlying API endpoints, database schema, or habitat model. The migration is purely at the MCP tool/interface layer. The habitat itself was already identified by `habitatId` everywhere below this layer.

## Verification

- `@orcy/mcp` tests: 37 files, 693 tests passed.
- `@orcy/mcp` typecheck: clean.

## No operator action required

No schema changes, no migrations. Legacy `boardId` callers continue to work through transparent fallback. New integrations should use `habitatId`.
