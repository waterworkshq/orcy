# v0.40.2 — Patch: Complete habitat settings shapes and corrected MCP docs

A review-comment audit of the PR history surfaced three residual findings; this patch fixes all three. Two share one root: a partial settings PATCH against a habitat that had never stored settings persisted the partial object verbatim, violating the complete shapes the API declares — and for anomaly settings, crashing the next anomaly scan.

## Settings PATCHes now persist complete objects

The first-ever `PATCH /habitats/:id` carrying `anomalySettings`, `triageSettings`, `releaseSettings`, or `roadmapSettings` on a habitat with no stored settings now merges the partial input over the canonical defaults for that blob, recursively for nested fields. Before, the stored object was exactly what the caller sent: an anomaly-settings PATCH of `{"enabled": true}` persisted a blob with no `thresholds`, and the next anomaly scan crashed with a TypeError dereferencing the missing stale-in-progress threshold. Partial nested patches also dropped sibling fields — patching one threshold value replaced the whole thresholds object; nesting now merges per-field.

Stored rows that were already partial (written before this fix) are healed on read: anomaly-settings resolution fills per-field defaults the same way release and roadmap settings always have.

## Raw consumers see complete shapes

PATCH responses, the stored habitat row, and habitat manifest exports now carry the complete declared shape for release and roadmap settings — previously all three could surface a partial object to anything reading the raw blob rather than the defaulting services. Contract tests pin the response, store, and export paths, and a guard iterates every settings blob with canonical defaults so future settings keys inherit the same guarantee.

## MCP docs no longer advertise a removed action

The shipped MCP usage skill and the install/architecture docs still listed the `update-settings` habitat-dispatch action that v0.36.0 removed; agents following the docs got `Unknown action`. The action is gone from the skill's action table, its example (replaced with `get-settings`, with a note that habitat updates go through the human-authenticated PATCH route), and both reference docs. The `orcy habitat update-settings` CLI command is unaffected. A docs-consistency test now fails if any doc advertises a habitat-dispatch action the dispatcher does not implement.

## No operator action required

Behavior is strictly hardening. Habitats that already hold partial settings blobs will simply start returning complete, default-filled shapes. No migration, no configuration.
