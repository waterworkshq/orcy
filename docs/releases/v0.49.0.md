# v0.49.0 — Zod 4 Validation, Request Collection Caps, Dependency Majors, Install Alignment

v0.49.0 migrates request validation across the API and shared schemas to Zod 4 (with `fastify-type-provider-zod` 5), adds a root `preValidation` request collection and depth cap ahead of schema validation, authentication, and rate limiting, ships a read-only pre-upgrade stored-data audit script, and lands five major dependency upgrades alongside a 20-package minor/patch refresh. It also aligns the bootstrap installer (`install.sh`) and public installation/deployment documentation with the supported Node.js 24 (LTS) and 26 (Current) policy.

Before v0.49.0, request schemas ran on Zod 3, which accepted synthetic 8-4-4-4-12 hex strings as UUIDs and timestamps without seconds, while leaving unbounded request arrays and deeply nested payloads unconstrained until schema validation had already walked every element — and on schema-declared routes, that work happened before authentication and rate limiting. The `install.sh` bootstrap still only rejected Node majors below 20, allowing unsupported runtimes (such as Node 20, 22, 25, or 27) to download and overwrite `~/.orcy/src/orcy` before hitting workspace engine checks, and public install/deployment docs still carried stale Node 20 and Bun references.

---

### Zod 4 Request Validation and Stored-Data Audit

Request validation across `@orcy/api`, `@orcy/shared`, and `@orcy/mcp` now runs on Zod `4.6.7` and `fastify-type-provider-zod` 5. Single-argument `z.record` schemas, `ZodError.issues` readers, and deprecated `ZodTypeAny` references are migrated, and omitted keys on `z.unknown()` fields remain optional where the v3 contract allowed them (`exists`/`not_exists` automation conditions omitting `value`, and `preserve`/`reset` habitat import domain envelopes omitting `data`; `replace` import envelopes now explicitly require `data` through a discriminated union on `disposition`).

Validation is stricter than under Zod 3:

- **UUIDs** validated with `.uuid()` must be RFC 4122 / 9562 versioned UUIDs (plus the nil and max UUIDs); synthetic hex strings with invalid version or variant nibbles are rejected.
- **Timestamps** validated with `.datetime()` require explicit seconds (`YYYY-MM-DDTHH:MM:SSZ`, with optional fractional seconds), and routes that accept numeric timezone offsets require a colon in the offset (e.g. `+05:30`, not `+0530`).
- **Validation error responses** use Zod 4 default messages (custom schema messages are unchanged), and routes declaring Fastify `schema` validation return `details` as an array of Fastify validation error items (`keyword`, `instancePath`, `schemaPath`, `message`, `params`) rather than a nested `params.issue` wrapper. Handler-side `safeParse` routes keep `details.fieldErrors` / `formErrors`.

One narrow read-compatibility exception protects existing live remote grants: `evaluateGrantTime` normalizes legacy stored `remote_grants.expires_at` values in UTC minute precision (`YYYY-MM-DDTHH:MMZ`) to `:00Z` on read before validating with `z.string().datetime()`. New grant provisioning requests, server-generated `expiredAt`/`revokedAt` timestamps, and all other non-canonical values remain fail-closed. Operators upgrading an existing database can run the new read-only `scripts/audit-zod4-stored-data.mjs` script (Node 24+, snapshot-based, counts only, never prints stored values or identifiers) before cutting over.

### Request Collection and Depth Caps

A root `preValidation` hook now bounds parsed request bodies and query strings before declared-schema validation, authentication, and rate limiting. Any request containing an array with more than **2,048** elements, an object with more than **2,048** keys, or nesting deeper than **64** levels (root container level 0; level 64 allowed; deeper containers rejected) is rejected immediately with a fixed-size `400 VALIDATION_ERROR` that echoes nothing from the request. No element of an oversized collection is validated.

Routes whose legitimate payloads scale with a whole board, workflow, or pull request raise the per-collection cap through route config, each derived from what the 1 MiB body limit holds for that route's smallest accepted wire record:

| Routes | Per-Collection Cap |
|--------|--------------------|
| Default (all other routes) | **2,048** |
| `POST /habitats/import`, `POST /habitats/:id/import` | **16,384** |
| `POST /missions/:id/workflow`, `PATCH /workflows/:id` | **16,384** |
| `POST /tasks/:taskId/code-evidence`, `POST /missions/:missionId/code-evidence` | **32,768** |

Non-object/non-array bodies (plain text, raw bytes, multipart uploads) carry no collections and are skipped. Caps are route constants rather than configuration settings, and each cap bounds one collection at a time while the 1 MiB request body limit and URL length limit bound the overall walk. A source-scan guard pins the inventory of request array schemas without explicit upper bounds; schema-level upper bounds on those remaining arrays are intentionally not planned, and `docs/API.md`, `docs/SECURITY.md`, and `docs/CAPABILITIES.md` are synchronized and guard-tested against the production constants.

### Major Dependency Upgrades

Five major dependency updates and one grouped 20-package minor/patch refresh land in this release:

- **`better-sqlite3` 12.9 → 13.2** — native SQLite driver refresh, verified on both Node 24 and Node 26.
- **`@tanstack/react-table` 8.21 → 9.3** — `DataTable` migrates to v9's explicit feature-set registration (`tableFeatures` with filtering, sorting, selection, visibility, and full built-in sort/filter registries so `auto` never silently degrades; unused `size` hints dropped).
- **`@fastify/static` 8.3 → 10.1** and **`fastify-raw-body` 5.0 → 6.0** — Fastify middleware majors, preserving `runFirst` raw-body capture ordering for HMAC-verified webhooks.
- **`@clack/prompts` 0.10 → 1.9** — interactive installer wizard updated for v1's `string | undefined` validator signature.
- **20-package minor/patch group** — `oxlint`, `@fastify/multipart`, `cron-parser`, `nodemailer`, `undici`, `sql.js`, `@tanstack/react-query`, `@tiptap/*`, `react-router-dom`, `recharts`, `@testing-library/dom`, `autoprefixer`, and `postcss`.

### Install Preflight and Documentation Alignment

`install.sh` now validates the full single-line `node --version` output (`v<major>.<minor>.<patch>`) and requires Node.js **24 (LTS)** or **26 (Current)** before downloading or replacing `~/.orcy/src/orcy`, stopping early on missing or unsupported versions (`20`, `22`, `25`, `27`, or malformed strings) with offline hermetic test coverage in `@orcy/installer`. `README.md`, `docs/INSTALL.md`, `docs/DEPLOYMENT.md`, `docs/TESTING.md`, and `CONTRIBUTING.md` are reconciled to the same Node 24/26 and Corepack-pinned pnpm policy (including installing `corepack@0.34.2` on Node 26 deployments where Corepack is not bundled, removing the broken `npx github:` install command and stale Bun checklist commands, and adding the public install docs and `install.sh` to the Node-version rollover checklist).

### What Stayed the Same

Database schema (zero new migrations; `0000_schema.sql` untouched), REST route inventory, MCP tool surface, SSE event types, authentication policies, plugin runtime, daemon, and CLI contracts. Existing habitat exports, workflows, and code-evidence payloads at normal board scale fit under the per-route collection caps.

### Operator Action Required

**Recommended pre-upgrade check for existing instances.** Before upgrading an existing SQLite database to v0.49.0, run the read-only stored-data audit script (requires Node.js 24+):

```bash
node scripts/audit-zod4-stored-data.mjs /path/to/orcy.db
```

Legacy stored `remote_grants.expires_at` values without seconds (`YYYY-MM-DDTHH:MMZ`) are tolerated on read so active grants do not lose authority across the upgrade. Any other non-zero count indicates stored legacy synthetic UUIDs or seconds-less timestamps that Zod 4 would reject if echoed back through the API — inspect and clean them or update affected API clients before cutting over.

API clients that parse validation error `details` on schema-declared routes or match default Zod error messages should verify compatibility against the Zod 4 / `fastify-type-provider-zod` 5 shapes documented in `docs/API.md`. Source checkouts should refresh dependencies with `corepack pnpm install --frozen-lockfile` on Node.js 24 (LTS) or 26 (Current) (on Node 26 without Corepack, run `npm install -g corepack@0.34.2` before `corepack enable`).

### Verification

- CI on `main` covers both Node 24 and Node 26 across the lint/test workflow (two parallel API shards, workspace suites, lint, all-package typecheck, Node 26 native `better-sqlite3` check) and the production migration gate.
- Dedicated regression and guard coverage pins the Zod 4 validation contract (`z.unknown().optional()`, `replace` import envelope, legacy grant deadline tolerance, stored-data audit script fixtures), the request collection and depth caps (every route tier at cap and one past cap, plus `documentationValidation` pinning documented numbers to production constants), TanStack Table v9 sort/filter registries, and the `install.sh` Node 24/26 preflight (20/20 hermetic bootstrap tests).
