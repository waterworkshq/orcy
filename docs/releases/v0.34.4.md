# v0.34.4 — Fix: code-evidence wire-name mapping + typed MCP handlers

Fixes a 400 on the `correct-code-evidence-link` MCP action and wires descriptor-derived handler typing that surfaced the drift.

## `correct-code-evidence-link`: map wire names to backend + wire `ArgsOf` handler typing

**Fixes a 400:** the `correct-code-evidence-link` MCP action was broken end-to-end. The agent-visible wire delivered `linkStatus`/`correctionReason`, but the backend route's `correctLinkSchema` requires `status`/`reason`, and the handler rest-spread the wire names straight through — so every call failed validation. The handler now maps `linkStatus`→`status` and `correctionReason`→`reason` before calling the API.

**Type-safety payoff (what surfaced the bug):** `ActionEntry` is now generic — each handler's `args` type derives from its descriptor entry via `ArgsOf<A>`, killing the `args: any` erasure at the inline handler arrows (`args.bordId` is now a compile error, not a silent runtime bug). Method-syntax bivariance lets named handlers keep their own already-typed `args`. Wiring this typing is what surfaced the wire/backend name drift above.

The legacy `code-evidence` unit test is now an honest wire→backend integration test (calls the handler with wire names, asserts the client receives backend names).

> The same wire/backend name-drift pattern likely affects `mark-not-applicable`, `report-gap`, `resolve-gap`, and the mission-level evidence variants — tracked separately for audit (`mcp-code-evidence-wire-name-drift`).
