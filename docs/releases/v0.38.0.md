# v0.38.0 — Learning Loop

v0.38.0 ships the Learning Loop: a bounded, human-governed proposal loop that converts an allowlist of trustworthy Orcy history into immutable, cited findings, and feeds the accepted ones back into Habitat knowledge and bounded agent context. A core-owned source catalog extracts from task and mission lifecycle audit events, terminal automation and plugin runs, terminal triage resolutions, and a new privacy-projected experience aggregate; pure built-in extractors propose lessons, conventions, risks, anomalies, prose-only rule recommendations, and knowledge drafts; local humans review each proposal through a compare-and-set decision flow; and accepted findings can be promoted into a Habitat Wiki draft or read by an agent working an active task. Two ADRs record the contracts: ADR-0044 (the extraction ledger, citations, lineage, and logical-work/attempt identity) and ADR-0045 (authorization and privacy propagation, including the actor-bound agent read predicate).

Before v0.38.0, Orcy accumulated rich operational history — audit events, triage outcomes, experience signals — but had no mechanism to extract reusable, cited lessons from that history and route them into knowledge and agent context. Pulse insights, habitat skills, and the Living Library each captured pieces, but nothing closed the loop from trusted sources through human review to durable, permission-aware knowledge. The Learning Loop fills that gap deliberately and narrowly: it never autonomously modifies rules, tasks, or published knowledge, and it never widens the audience of the history it consumes.

---

### The Extraction Ledger

Eight new tables own the complete lifecycle: enrollment policies, replay-safe logical work items, fenced physical attempts, immutable cited finding revisions, polymorphic citations, server-derived authorization scope refs, append-only review history, and at-most-once destination promotions. The design separates logical work (what was extracted for a given window and policy) from physical attempts (each execution), so a scheduled delivery and a manual replay of the same envelope converge on one work item, while an explicit human-only fresh rerun opens a new monotonic generation linked to its predecessor. Findings are immutable content-and-evidence revisions: re-observing identical claim and evidence advances recurrence counters only, and changed evidence creates the next linked revision rather than overwriting the prior one. Lease generation fences every persistence and terminalization step, and exactly-once completion belongs only to the owned running-to-terminal transition.

### The Source Catalog

A total, core-owned catalog governs which history may enter the loop. Each enabled family owns stable identity, version semantics, boundary capture, visibility classification, and a direct family-specific resolver — task and mission lifecycle audit events, terminal automation runs, terminal plugin runs, and terminal triage resolutions round-trip through collect, persist, and resolve. Resolvers distinguish available, dangling, unauthorized, and changed at read time by direct lookups (never a whole-habitat rebuild), and a changed or dangling citation marks a finding stale without deleting prior review or an already-authored page. Operational families carry only their own identity and never project task or mission scope, leaving their findings human-only for agent reads.

### Experience Privacy Projection

Experience signals enter the loop through a dedicated privacy projection that is strictly stronger than the shipped aggregate surface. A non-configurable floor — at least five signals from at least three distinct agents, in windows of at least seven days — admits cohorts only on counts recomputed inside the captured extraction window, not all-time aggregates. Every isolating field is suppressed before the extractor ever sees data: individual identifiers, raw bodies, exact timestamps, and rare singleton combinations are removed, a transient denylist scans candidate text and is then discarded, and only coarse windows and banded counts cross the boundary. When window membership cannot be verified, admission fails closed rather than falling back to historical counts, and a cohort that later drops below the floor withdraws its finding from agent reads without revealing why.

### The Execution Lifecycle

One fenced seam serves every delivery path — the scheduled scan, a manual ensure, an explicit reason-required fresh rerun, a dry run, and boot recovery. The scheduler honors the policy cron; a dry run exercises real collection and validation but persists no findings; and boot recovery reconciles stale running attempts and crashed-after-commit work using the committed findings themselves rather than unreliable tallies, resuming replay-safe through the same seam with the originally captured window and boundaries. Partial and failed runs record honest per-source diagnostics, a failed source never advances its watermark or appears as an empty success, and detector failures mark the attempt partial rather than masquerading as a successful source.

### Human Review and Authorization

Local humans review proposed findings through a queue and detail view with compare-and-set decisions — accept, reject, request revision, and withdraw — each guarded by an expected decision version so concurrent reviewers produce one winner and one conflict. The decision state machine is explicit: a withdrawn or rejected finding cannot be resurrected back to accepted, and withdrawal is recorded as its own decision so privacy or integrity invalidation is distinguishable from human rejection. Citation degradation (dangling, changed, or unauthorized) blocks new promotion and is re-checked on every agent read, because captured visibility is evidence rather than a permanent grant.

### Bounded Agent Reads

An agent may read accepted findings only in the context of a supplied active task. The authorization is a single joined SQL predicate that ties every result to the task's assignment and active status, its mission and habitat, the finding's readable state and visibility, and an exact server-derived task, mission, or required-domain scope ref — there is no habitat-wide fallback, and client filters may only narrow the authorized set. Reassignment or terminalization before the query removes access with no separate precheck race, and denials collapse not-found and forbidden into one response that reveals no existence. A read-only `orcy_learning` MCP tool exposes the same two actions, returns bounded summaries under a hard limit and total character budget, and carries no raw source or experience-contributor data.

### Wiki Draft Promotion

Accepting a finding and promoting it are separate acts. Promotion creates at most one Habitat Wiki **draft** through the existing wiki service — never a published page — and is crash-safe: a retry after an interrupted promotion reuses the already-created page by a deterministic idempotency key rather than creating a duplicate. The successful promotion row, not the removable wiki link, is the permanent derivation record, so deleting the citation, editing the page, or publishing it cannot re-expose that page as a future extraction source. Acceptance never automatically publishes knowledge or enables an automation rule; rule recommendations are prose only.

### What Stayed the Same

The plugin system, daemon, CLI, local task lifecycle, automation engine, triage, audit projection catalog, and remote participant transport are untouched. No existing REST route, MCP tool, or SSE event type changed behavior; the three new extraction SSE events are additive and carry only bounded finding state. The shipped Living Library experience surface and Habitat Skills are unchanged — the Learning Loop consumes history alongside them, it does not replace them.

### Schema Changes

- **New tables (migration `0063_learning_loop_ledger`):** `learning_loop_policies`, `extraction_work_items`, `extraction_attempts`, `extracted_findings`, `extracted_finding_sources`, `extracted_finding_scope_refs`, `extracted_finding_reviews`, `extracted_finding_promotions`. Drizzle schema mirror at `packages/api/src/db/schema/extraction.ts`.

### Operator Action Required

**None to upgrade safely.** The Learning Loop is dormant by default: it runs only when both the global `ORCY_LEARNING_LOOP_ENABLED` flag and a per-habitat policy's `enabled` setting are on. Disabling stops new runs and promotions while accepted reads remain available. To turn the feature on for a habitat, set the global flag and enable a policy through the new Habitat settings surface; no migration or config conversion is required.

### Verification

- Full API, MCP, shared, and UI suites green; production migration chain and compiled-startup gates pass on both SQLite backends.
- A focused extraction suite plus a discriminating failure-injection suite and a better-sqlite3 parity suite cover the fencing, compare-and-set, atomicity, privacy-floor, crash-recovery, and authorization boundaries. The feature passed four independent adversarial reviews before release.
