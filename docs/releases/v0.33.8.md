# v0.33.8 — Patch: publication-kernel + automation-scan correctness fixes

> **Type:** patch (defect correction + documentation accuracy)
> **Severity:** moderate (latent contract gap + observability metrics + scan over-firing)
> **Migration required:** none (no schema change, no flag)
> **Operator action required:** none — one behavior correction noted below

## Summary

Three correctness fixes accumulated since v0.33.7, plus a documentation-accuracy sweep. No schema migrations, no breaking changes, no feature additions.

1. **Task-creation committed-identifier projection.** Four columns on `task_creation_attempts` (`committedTaskId`, `committedMissionId`, `envelopeEventId`, `reservationId`) shipped with no production writer — they stayed null even after an attempt committed a Task/envelope/reservation. `committedTaskId` is the UI contract read on the `created_unassigned` (targeted-assignment refusal) recovery terminal; a null value broke that surface. They are now populated at the first commit point.
2. **Automation scan tally propagation.** The three standalone automation scans (agent-quality, signal-pattern-clustered, orphan-mission) reported `rulesMatched` / `rulesSkipped` / `rulesDeduplicated` as always `0` in every `ScanReport` — the tally counters were passed by value, so the increment mutated a throwaway copy. Rules still executed; only the reported metrics were broken. Counters now propagate correctly.
3. **Agent-quality threshold unit mismatch.** `runAgentQualityDegradedScan` compared the raw 0–1 composite score against the 0–100 `agentQualityThreshold` (default 40; schema `int 0–100`; UI percent input), so `score >= threshold` was always false and **every** agent with an adequate sample was flagged degraded on every scan cycle. The gate now normalizes (`score * 100 >= threshold`).

## Operator-Facing Changes

### Behavior Changes

| Before v0.33.8 | After v0.33.8 |
|---|---|
| `GET /task-creation-attempts/:id` returned null `committedTaskId` / `committedMissionId` / `envelopeEventId` / `reservationId` even for committed attempts | All four are populated at the commit point; `committedTaskId` is available for the `created_unassigned` recovery UI |

| Agent-quality-degraded scan flagged **every** agent with an adequate sample as degraded (over-firing) | Only agents whose composite score is below the configured `agentQualityThreshold` are flagged |

### Compatibility

- No database migration. No flags. No config changes.
- The agent-quality correction is a behavior change for operators with `agent_quality_degraded` automation rules: such rules now fire only for genuinely-degraded agents (score below threshold). No rule edits required — the threshold you configured now behaves as the percentage it was always presented as.
- The committed-identifier population is additive (columns that were null are now populated); no reader regressed.

### Documentation Accuracy

Swept the stale "DORMANT / exercised only by tests until cutover (T11)" headers across the publication kernel and its tests. The Task-creation cutover landed in v0.32.0 (`isCreationPublicationEnabled` is always true; legacy create/clone routes removed), so the kernel is the sole Task-creation path — the dormancy framing no longer held. Doc-only; no behavior change. `scheduledHandlerDispatch` was confirmed live (non-Task-producing but exercised via `handlerKey` schedules such as the wiki-cadence handler).
