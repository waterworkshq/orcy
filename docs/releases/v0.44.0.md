# v0.44.0 — Scoped Roles and Governed Review Management

v0.44.0 adds a bounded local authorization foundation for configuring review policy and assigning reviewers. Human governors can manage immutable role revisions and scoped assignments, while review-management writes evaluate current authority and commit their changes with governance audit in one transaction. Team administration and destructive custody changes now recheck persisted human authority at the write boundary.

Before v0.44.0, local review management relied on broad global roles and Team membership checks rather than explicit operational grants. Role administration had no served scoped command surface, and a Team administration request could retain authority from an old JWT or a membership check made before the write reservation. This release separates current human governance from narrowly delegated review operations and retains the evidence needed to explain both.

---

### Scoped Operational Roles

The permission catalogue contains `review.configure` for Habitat review rules and `review.assign` for Task reviewer rosters. The built-in Coordinator and Review Coordinator roles provide starting points; custom Team- or Habitat-namespaced roles carry immutable revisions, and assignments pin a revision to a typed human or agent. Grants follow the target's current ancestry and scope incarnation, and expiry is checked when authority is used. Revocation retains history rather than deleting evidence. These permissions do not confer general administration, Task execution, approval, or rejection authority.

### Human Governance and Personal Ownership

Human-only HTTP commands expose the permission catalogue, role definitions and revisions, assignments, and personal-Habitat ownership. Administrative mutations require current persisted governance, scope and object expectations, and an atomic audit write; an audit failure rolls the mutation back. Global viewers cannot gain governance through Team ownership or an operational grant. Existing personal Habitats are not assigned an owner from history: they remain global-admin governed until a global admin explicitly sets an owner. There is no MCP role-administration tool or graphical role editor in this release.

### Transactional Review Management

Review-rule creation, update, and deletion now require `review.configure`; manual reviewer additions and removals require `review.assign`. A current persisted governor supplies the governance adapter, while other local humans or agents need an explicit applicable grant. Rule updates accept optional `expectedVersion`; roster writes accept optional `expectedReviewersToken`. Supplied stale expectations return a conflict without mutation, while omission preserves the existing versionless compatibility behavior. Reviewer reads return their roster and token from one consistent snapshot, including requirement state and the actual typed reviewer rows. Assignment does not grant lifecycle decision authority, and the existing anti-self-review checks remain.

### Custody, Deletion, and Restore

Managed deletion retires affected scope lifetimes, role namespaces, and grants in the same reservation as the resource mutation. Team deletion leaves surviving descendant Habitats with fresh scope incarnations and no carried-over grants. Authorized same-lineage Mission and Task restores also use fresh lifetimes without reactivating old authority. Team deletion and membership add, role-change, and removal reread the live user and Team governance inside their IMMEDIATE transaction; stale JWT roles or lost membership cannot authorize a write. Creating a Team-bound Habitat requires human governance and a current Team scope expectation. Raw database writes remain outside these managed guarantees.

### Startup and Upgrade Verification Reliability

Compiled API boot tests now build into private per-suite output directories, preventing a parallel compiler from truncating modules while a startup child imports them. The pre-upgrade SQLite fixture uses the same WAL journal mode as production, removing expensive rollback-journal setup commits under full-suite load. These are test-only changes: default parallelism, the upgrade test's five-second limit, production startup behavior, and migration assertions are preserved.

### What Stayed the Same

The durable review-safety contract from v0.43.0 remains intact: captured requirements, immutable claim snapshots, generation and round semantics, committed finality proof, known-zero-only merge approval, and independent human recovery. Ordinary reads, Task execution and review decisions keep their existing authority boundaries; remote participants, trusted system integration paths, and internal allocation remain separate. Existing review-rule and roster clients may omit the new optional conflict expectations. No new MCP tool, configuration variable, or general role-management UI is introduced.

### Schema Changes

Migration `0083_role_foundation_governance` adds `governance_scopes`, `role_definitions`, `role_revisions`, `role_assignments`, and `governance_audit`. It also adds nullable `habitats.owner_user_id` and the version counter on `review_rules`, and seeds the fixed built-in role revisions. Existing resources receive the initial governance scope state; existing review rules start at version 1. The migration does not infer personal owners or backfill operational assignments, and it leaves retained review-safety evidence unchanged.

### Operator Action Required

**Review callers of review-management writes before upgrading.** Team membership alone is no longer sufficient to configure rules or change reviewer rosters: callers must be current governors or hold the corresponding scoped operational permission. Global viewers remain refused. Use a human governor to issue the required assignments, and explicitly set owners for personal Habitats where non-admin governance is intended. Agent-authenticated role administration is not supported.

The additive migration runs through normal API startup; no manual SQL or new environment setting is required. Back up the database before the upgrade using the deployment procedure. Custom clients that create Team-bound Habitats must supply the current Team scope expectation described in the API contract; the Web UI fetches a fresh expectation on each submission. Rule and roster conflict expectations remain optional, but clients using them should refresh after a conflict rather than replay stale values. See [API.md](../API.md), [SECURITY.md](../SECURITY.md), and [DATABASE.md](../DATABASE.md) for the callable and storage contracts.
