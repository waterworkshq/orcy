# v0.35.0 — Deepen: Remote Participant Actions

v0.35.0 gives the `/api/shared/*` Remote Participant surface one transport seam so that a remote claim/submit/release produces the same observable lifecycle as a local one — same canonical Task Event, SSE, watchers, mission recalculation, auto-pulse, and subscriber hooks — while closing two long-standing gaps: governance interceptors were bypassed for remote transitions, and Host-Approved Capability was never enforced for remote claims. ADR-0043 records the transport-seam contract (the seam-level counterpart to ADR-0038). A local↔remote parity-contract test pins that a remote mutation now matches the local side-effect set, modulo actor type and the remote-only cross-pod notification.

Before v0.35.0, the remote claim/submit/release handlers called the repository directly and hand-rolled a manual Task Event plus a cross-pod notification. That path skipped `emitTransition`'s full side-effect fan (so remote mutations didn't trigger automation, audit-projection lifecycle capture, realtime SSE, or mission recalculation), skipped the service-wrapper's governance interceptors entirely, and never checked Host-Approved Capability. The route catch also swallowed any post-mutation side-effect failure as idempotent 200 success. Comments inverted the drift, over-emitting a manual event plus a wrongly-typed notification the local route does not produce.

---

### The Remote-Task-Lifecycle Seam

A new `services/tasks/remote-task-lifecycle.ts` module is the only place that knows the remote actor model. Three wrappers — `claimTaskForRemote`, `submitTaskForRemote`, `releaseTaskForRemote` — resolve remote policy (eligibility, governance) and delegate to the same shared infrastructure the local path uses. The local wrapper stays transport-pure; the convergence point is shared infrastructure, not a shared function. Boundary: the wrappers OWN actor mapping, eligibility, governance invocation, and cross-pod notification; DELEGATE mutation to the tx-injecting authority primitives + side-effects to `emitTransition`; and KEEP the four task-intrinsic guards inside the claimability authority per ADR-0038 (they are not re-checked).

### Atomic Mutation + Event

Each wrapper opens one transaction and composes only the tx-injecting primitives (`*WithClient`) — the mutation and the canonical Task Event commit together or not at all. `emitTransition` gained an additive optional `existingEventId`: when set, it reuses the transaction-committed event instead of creating its own, so the side-effect fan fires exactly once with no double event. `TransitionContext.actorType` was widened to the canonical `ActorType` (adding `remote_orcy`/`remote_human`); the narrow cast is gone. This is the same transaction-composition pattern the v0.34.0 workflow-gate advancer validated.

### Governance + Capability — Active by Default

Two behaviors ship **ON by default**, resolved by a two-layer kill switch — env `ORCY_REMOTE_GOVERNANCE_DEFAULT` (global) + a per-habitat `remoteGovernanceSettings` JSON column (override) — mirroring the `automationSettings` precedent:

- **Governance interceptors** — a remote claim/submit now runs the same pre/post interceptors as a local one. A veto reuses `INTERCEPTOR_VETO` (403) with the blocker detail suppressed for the remote client.
- **Host-Approved Capability** — a remote claim checks the participant's `approvedCapabilities` against the task's `requiredCapabilities` using the same predicate as local.

### Partial-Completion Honesty

The old route catch treated "mutation landed, side-effect threw" as idempotent 200 success. With the new atomicity, a veto or transaction failure rolls back and is reported honestly; idempotency stays the route envelope, never weakened to mask a failure.

### Comments as Advisory Feedback

The remote task-comment handler dropped its manual `action:"updated"` Task Event and its wrongly-typed notification. Both local and remote comment routes now reduce to `commentService.addComment`, which already fires the real SSE + hooks — that is the seam. Mission comments already matched.

### Anti-Probing Info-Disclosure Hardening

The remote surface follows the 404/403 convention (404 prevents blind enumeration; 403 for authenticated-but-unauthorized). The two existence-leaking denial codes — cross-habitat-mismatch and not-visible — are now collapsed to a generic 403 for the client (the specific reason is logged server-side only), so a cross-habitat participant cannot distinguish "exists elsewhere" from "exists here but invisible" by probing task IDs. Ownership-feedback denials remain a distinct 403 (not an existence leak).

### Heartbeat Presence — Dedicated `lastActivityAt`

The remote heartbeat no longer bumps the general-purpose `updatedAt` (which conflated presence pings with real modifications). A dedicated `lastActivityAt` column records the last heartbeat presence signal; the response returns the persisted value instead of a fabricated timestamp.

### Remote-Creator Fidelity in Task-Creation Dispatch

The async task-creation dispatch adapter no longer collapses a remote creator's actor type down to the local `agent`/`human` union — a workaround for the pre-widened `TransitionContext` type. Remote creators are now attributed faithfully (`remote_orcy`/`remote_human`) through the dispatch path.

### Subscriber + Production-Data Audit

A direct audit of every Task-Event-row consumer confirmed no `actorType` filter silently drops remote-originated rows; the per-agent metric queries (which intentionally filter to `agent`) form the agent-quality contamination fence, correctly excluding remote activity. There are no in-repo `taskClaimed`/`taskSubmitted` interceptors. The audit cleared the in-repo surface; flagged follow-ups are recorded in `docs/deferred/`.

### What Stayed the Same

ADR-0038's claimability boundary (four task-intrinsic guards at the mutation), ADR-0005's two-channel subscriber contract (the `existingEventId` + widened `actorType` are additive), and ADR-0014's interceptor veto contract. The plugin system, daemon, CLI, local task lifecycle, and MCP surface are untouched. No new REST routes, MCP tools, or SSE event types.

### Schema Changes

- **New column:** `habitats.remote_governance_settings` (JSON, nullable) — migration `0061`.
- **New column:** `tasks.last_activity_at` (text, nullable) — migration `0062`.

### Operator Action Required

**Review remote-participant capabilities before upgrade.** Host-Approved Capability enforcement is now ON by default: a remote participant whose `approvedCapabilities` is empty (the default) will be **refused** when claiming a task that carries `requiredCapabilities`. If you have remote contributors working on capability-bearing tasks, approve their capabilities (via the admin path) before upgrade, or set `ORCY_REMOTE_GOVERNANCE_DEFAULT=false` (global) or the habitat's `remoteGovernanceSettings.enforceHostApprovedCapability=false` (per-habitat) to preserve the prior behavior.

Governance interceptors are also ON by default: remote claim/submit transitions now run enrolled `taskClaimed`/`taskSubmitted` interceptors. If you run user-installed interceptors that assume a local actor type, verify they handle the widened `actorType` (`remote_orcy`/`remote_human`).
