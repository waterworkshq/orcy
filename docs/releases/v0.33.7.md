# v0.33.7 — Fix: Mandatory Automation Rule Conditions (CS-56)

> **Type:** patch (defect correction)
> **Severity:** BLOCKER (production correctness + safety)
> **Migration required:** none (no schema change, no flag)
> **Operator action required before upgrade:** yes — see [Action Required Before Upgrade](#action-required-before-upgrade)

## Summary

Automation Rule conditions are now **mandatory production gates**. Every trigger-selected rule evaluates its stored `condition` before any configured action runs. `{type:"always"}` remains the explicit trigger-only rule.

This corrects a production defect introduced when v0.20.1 activated action execution across events and scans: the live path built the evaluation context but never invoked the evaluator, so every trigger-matched rule fired its actions regardless of its stored predicate, and production `conditionResult` stayed null. v0.33.7 wires the evaluator in and consolidates all eight production call sites (event ingestion + seven scheduled-scan families + manual route) behind one canonical rule-attempt lifecycle.

## Operator-Facing Changes

### Action Required Before Upgrade

**Simulate every enabled non-`always` Automation Rule against current state to confirm intended behavior.** Non-`always` rules begin behaving as authored on upgrade. Rules whose stored condition evaluates to false against current triggers will switch from "fires actions" to "skipped with `skipReason=condition_false`".

This is a behavior change, not a config change — your existing rules keep their conditions; they just start being honored.

### Behavior Changes

| Before v0.33.7 | After v0.33.7 |
|---|---|
| Trigger-matched rule fires actions regardless of stored condition | Trigger-matched rule evaluates stored condition; false → no action, persists `condition_false` |
| Malformed or depth-exceeded condition falls back to unconditional execution | Malformed or depth-exceeded condition **fails closed** as `status=failed` with bounded diagnostic — no actions fire; surface for repair |
| Action kill switch records `status=succeeded` (no run result distinguishing the skip) | Action kill switch records `status=skipped`, `skipReason=disabled`, persists the **true** `conditionResult`, no actions fire |
| `rate_limited`/`cooldown`/`missing_target` rejected rows extend the hourly admission window | Hourly admission counts **admitted attempts only** — rejected rows no longer prolong lockout |
| Duplicate trusted `task.created` delivery creates two `running` rows + double execution | Duplicate trusted `task.created` delivery owns **one** run and at most one action |
| Manual run (`POST /automation-rules/:id/run`) strands a `running` row without evaluating/executing | Manual run executes synchronously through the canonical lifecycle; returns terminal run + disposition |
| Live `raw.*` event conditions see only `{targetType, targetId}` (no event data) | Live `raw.*` event conditions see full `event.data` as `trigger.payload` — parity with simulation |
| `{type:"always"}` rules run actions on trigger | `{type:"always"}` rules continue to run actions on trigger (unchanged) |
| `{type:"always"}` rules with `enabled=true` (default) | unchanged |

### Compatibility

- No database migration. No `evaluateConditions` flag. No per-rule opt-in.
- `{type:"always"}` rules retain their current action behavior.
- Non-`always` rules begin behaving as authored.
- Existing malformed/depth-exceeded conditions fail closed and surface for repair; they are not grandfathered into unconditional execution.

### Repair Guidance for Existing Malformed Conditions

If any rules fail closed after upgrade, repair their stored condition against the new recursive depth-bounded `AutomationConditionSchema`:

- Max nesting depth: 5
- Restricted `field` roots: `task` / `mission` / `habitat` / `agent` / `sprint` / `raw`
- Built-in shape discrimination per `type` discriminator
- Comparison operators and required fields validated per discriminator
- Plugin `params` remain passthrough; structural plugin-node errors are invalid configuration and fail the attempt
- `not` requires a child; `and`/`or` may be empty (preserves prior semantics)

### Manual Run API Change

`POST /automation-rules/:ruleId/run` is now a synchronous terminal attempt route. Request body:

```ts
{
  targetType?: AutomationTargetType; // defaults to "none"
  targetId?: string;                 // required unless targetType is "none"
  payload?: Record<string, unknown>; // defaults to {}
}
```

Response: the terminal run + `AutomationAttemptDisposition`. The stored rule must exist and be enabled. The caller **cannot** override the stored condition, trigger identity, dedupe identity, or causal context. Task/Mission/Sprint/Pulse/Habitat targets must resolve to the rule Habitat. Agent targets require active Task work in the rule Habitat. Unsupported Integration targets are rejected until an ownership resolver exists.

Manual bypasses trigger occurrence only. It obeys target validation, cooldown, hourly admission, condition evaluation, causal defaults, and the action kill switch.

### Audit + History Projection

Run rows and audit projection now expose `conditionResult` (the evaluated predicate tree) and `conditionType` (`true` / `false` / `invalid`) for every terminal branch: false-condition skip, true execution, causal-cycle/depth skip, kill-switch skip, and invalid-evaluation failure.

### Workflow Gate Visibility

The settled kill-switch outcome is intentionally visible to Workflow Gates as `outcome=skipped`, not `succeeded`. Existing broad skipped gates may therefore match it — consistent with the gate's authored outcome selection.

`on_automation` Workflow Gates configured for `outcome=skipped` receive exactly one completion signal per owned terminal skip in the live process. Dedupe losers and failed persistence never emit.
