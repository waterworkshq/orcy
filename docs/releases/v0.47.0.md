# v0.47.0 — Deepen: Verified Task and Mission Writes

v0.47.0 gives the three places a human or integration most often damages state — editing a Task, admitting external work into a Mission, and stamping a Task complete — one verified, atomic write each. A human metadata edit is now a single immediate-transaction write that authorizes against persisted rows, fences the opening version and priority, and refuses a replaced Task outright; a work-source admission commits the Mission, its external link, and the candidate disposition together; and completion timing only commits when finality itself commits. Around those, the release consolidates Mission authoring and scheduled-occurrence execution behind single owners, and lands a batch of task-authority, recovery, and notification fixes.

Before v0.47.0, the Task detail modal's Save button was a disabled placeholder — correcting a typo meant the agent PATCH route or nothing. The generic Task update checked the version in one statement and updated in another whose filter was the ID alone; the prioritization writer changed priority without bumping the version, so a stale editor could silently overwrite a reprioritized Task. Promoting an intake candidate wrote the Mission, then the link, then the candidate disposition as separate commits — a failure midway left orphaned Missions that retries then duplicated. Completion metrics were written before review finality, so a Task refused at review could carry completion timestamps for work that never finished. And Mission Create/Edit each carried their own copies of the authoring rules, drifting apart in feature mode and version handling.

---

### Human Task Metadata Editing

Authorized humans edit a Task's title, description, and priority in the live Task detail modal through a new human-only route (`PATCH /tasks/:id/metadata`). The save is one `BEGIN IMMEDIATE` reservation that reads persisted authority (team membership plus an `editor`/`admin` user row; on personal Habitats the persisted owner or a global admin), checks the Task is still pending and unassigned in a live Mission, and updates exactly the changed fields. The write is fenced on the opening version, the opening priority (the prioritization writer changes priority without a version bump), and a SHA-256 identity over the Task's creation-envelope history — so a Task replaced under the same ID, even at the same version and timestamp, refuses instead of being silently overwritten. The update is proven by its returned row plus a full postimage comparison before anything is committed; an unchanged request is a zero-write no-op; native lock contention answers 503 with a `Retry-After` hint and no retry; exactly one `updated` audit event commits with a changed save. Task detail exposes `canEditMetadata` and `metadataEditIdentity` to human callers as a per-account UI affordance — a hint, never write authority; agents and ineligible viewers see none. The modal stays read-only by default, keeps an unsaved draft across background refreshes, and confirms before discarding it on close or task switch; refetches never advance the editing baseline. The agent `PATCH /tasks/:id` route and every other Task writer are unchanged.

### Atomic Work-Source Mission Admission

Promoting an intake candidate — or auto-importing an external issue — now commits the new Mission, its external-issue link, and the candidate's disposition in one synchronous SQLite transaction, through a single admission owner. The orphaned-Mission failure modes are gone: a link or candidate write that fails mid-admission rolls the whole admission back, and a retry after a partial failure meets the existing link and updates it instead of creating a duplicate Mission. An external identity already owned by another connection is refused with a bounded 409 that discloses no owner details. Automatic-import audit remains a post-commit effect whose failure propagates after persistence.

### Completion Timing Belongs to Finality

Completion timestamps now commit only with successful review finality, inside the same transaction: a timing or readback failure rolls the terminal state and the timing back together and emits no success effects. Independently useful evidence — supplied artifacts, review notes, and best-effort effort recalculation — persists as soon as preparation is reached and may legitimately survive a later finality refusal. The metric failure rollback is scoped to the terminal/timing bundle, not to prior evidence. Review requirements, proof and generation gates, approval behavior, and typed refusal contracts are unchanged.

### Mission Authoring and Scheduled-Occurrence Consolidations

Mission Create and Edit now share one Mission-specific authoring module for draft prefill and field serialization — Create's empty-value omission stays distinct from Edit's explicit null clearing, and an open Edit keeps its typed draft and baseline version across background refetches (a changed server version reports a conflict rather than silently rebasing). Scheduled-occurrence execution — timer/manual publication, reserved-occurrence takeover, and publishing-lease recovery — now routes through one execution module, preserving the distinct admission, snapshot, fencing, and event contracts of each operation.

### Task Authority and Recovery Fixes

The manual recovery ladder is safer and more honest: a rejected Task resets to the claim pool only under a writer that re-checks recovery authorization and the task's status-and-version preimage in the same transaction, so a revocation or rework landing mid-retry refuses with zero effects; stranded retries retire their due timers instead of escalating forever when the policy says not to; and ownership during escalation stays with the original owner. Task email recipients are authorized against the Task's Habitat rather than trusting the requester's list, MCP callers send canonical Habitat request keys, and the notification pipeline enforces explicit recipient intent end to end (with a delivery-cadence index backing it — see Schema Changes). On the client, habitat task lists refresh without request storms and mission queries batch during task suggestions; the daemon evicts terminal sessions from its live map.

### Plugin-Run Lifecycle Fixes

Notification delivery state is "cleared" only when actually cleared; prelaunch finish failures clean up their run rows; infrastructure veto reasons are sanitized before exposure; and operator-marked-lost runs record their operator and timestamp truthfully during recovery.

### What Stayed the Same

No changes to the agent Task update route, the prioritization writer, claim/delegation/publication reservations, governance privileges, schemas beyond one index, or any configuration surface. The unwired legacy task editor remains unwired. Both MCP SKILL copies, the HTTP API contract, and the audit-trail projections keep their existing shapes; the only API additions are the metadata route and the two detail-response hint fields.

### Schema Changes

One additive migration: `0088_notification_delivery_cadence_index.sql` — an index backing notification delivery-cadence checks. No new tables, columns, or constraints; no data migration.

### Operator Action Required

**None.** The single migration is an additive index applied by the normal migration runner on startup.
