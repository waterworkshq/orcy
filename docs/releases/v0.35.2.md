# v0.35.2 — Patch: Three gap closures + SSE null-guard

Three deferred items closed (RM-6 was already in v0.35.1; this release completes TG-15, RM-3B, and an unrelated SSE handler-safety fix) plus one test-infra cleanup. No schema migrations. No configuration changes. No breaking API contract changes.

## Fix 1 — PATCH `/api/missions/:id` now accepts `status` (close deferred TG-15)

The `updateMissionSchema` was missing the `status` field. Zod's default `.strip()` behaviour silently dropped `status` from PATCH bodies — version bumped (the route handler ran) but the field never reached the DB, leaving the mission's status unchanged. The downstream archive attempt failed (mission must be `done` to archive), and the previously-skipped archive e2e (15.3) was a false positive: it passed with no data because no data ever existed.

Add `status: z.enum([...]).optional()` to `updateMissionSchema` (`packages/api/src/models/schemas.ts`). The downstream repo mapper (`packages/api/src/repositories/mission.ts:229`) was already in place — the fix is purely declarative. Un-skip the 15.3 e2e test (`packages/ui/e2e/board-ux.spec.ts:132`); the click now uses `dispatchEvent('click')` to bypass a layout-level viewport issue (see Operator Notes). All 4 TG-15.* tests pass (15.1, 15.2, 15.3, 15.4).

## Fix 2 — SSE handler null-guard (independent of TG-15)

Every habitat page load was emitting a `PAGEERROR: Cannot read properties of undefined (reading 'notification')` — originating from `useSSENotifications.ts:40` → `getSSENotification` in `packages/ui/src/sse/registry.ts`. The handler lookup `SSE_EVENT_REGISTRY[type]` returned undefined for unknown event types, and the next access (`undefined.notification`) threw.

Change `getSSEEventHandler`'s return type to `SSEEventHandler | undefined` and add optional chaining (`?.`) at all three call sites (`getSSENotification`, `applySSEEphemeralUpdate`, `projectSSEServerEvent`). Unknown event types are now a no-op — the correct behaviour for a forward-compat registry: an SSE event the client doesn't know about shouldn't take down the page. The PAGEERROR was caught (Zustand subscription callback) so the React tree didn't crash, but it polluted the console on every habitat page load.

## Chore 3 — Add `critical_path` roadmap scoring selector (close deferred RM-3B)

RM-3B was documented since the v0.25.4 era as "never implemented". Add a fifth option to `RoadmapScoringAlgorithm` (`packages/shared/src/types/settings.ts`):

- `fanout` (default) — boost tasks that unblock many direct dependents
- `depth_from_root` — boost foundational work
- `release_proximity` — boost freshly-unblocked work
- `goal_directed` — boost the focus goal's prerequisite chain
- `critical_path` (new) — boost tasks on the longest dependency chain

Algorithm (`packages/api/src/services/roadmapScoring.ts`): load all `missionDependencies` edges for the habitat, build a `dependents` adjacency map, memoized longest-chain DFS with cycle guard (`visiting` set), proportional bonus `round(chain × MAX_BONUS / topChain)`. Reason text: `"On critical path (chain length N)"`. Edge cases handled: empty edge set → no bonus anywhere; cycle in DAG → treated as leaf (terminates the DFS); mission not in any edge → no bonus.

User-visible: the `critical_path` option now appears in the roadmap scoring settings dropdown. The four existing strategies are unchanged.
