# v0.40.0 — Restored Finding Triage Lifecycle

v0.40.0 restores the per-Engineering-Finding triage lifecycle as the live production authority, under one command kernel. Every triage write now flows through intent commands (`route`, `activate`, `resolve`, `wontfix`) executed inside a single immediate writer reservation — typed applied/replayed/conflict/busy outcomes, idempotent route fingerprints, atomic Mission+event+state+Resolution commits — while ad-hoc PATCH writers, the `/promote` endpoint, and the unlink patch shape are retired. ADR-0048 records the contract (superseding the conflicting portions of ADR-0026/0027/0029/0033; ADR-0032 remains authoritative).

Before v0.40.0, triage mutations were scattered ad-hoc writes: any client could PATCH lifecycle fields directly, terminal findings could be reopened, recurrence was derived from mutable cluster state, and the automation/release surfaces trusted request-time snapshots. Concurrent writers raced without a reservation, revoked remote credentials still authorized mutations, and deleting a Pulse or Mission could silently erase the history later releases would reconcile against.

---

### The Lifecycle Command Kernel

All triage writes go through four intent endpoints (local, shared, and MCP surfaces alike). The kernel opens `BEGIN IMMEDIATE` before any read, re-checks authority and eligibility inside the reservation, and commits the Finding state, its Mission, the audit event, and the Resolution as one unit. Every outcome is typed: contention returns **503 with Retry-After** (both local and remote surfaces, byte-identical codes), state races return typed **409** conflicts, and a network retry of an applied command replays idempotently against the stored route fingerprint. Terminal rows (`resolved`/`wontfix`) are immutable — recurrence requires lineage-novel evidence and creates a new row.

### Claim-Bound Authority

Agent routing is bound to the exact investigation Task's live claimant, locally or through `/api/shared` behind the `triage.route` scope (requiring an `Idempotency-Key`). The authority predicate re-reads credentials, participant standing, and grants **inside the transaction** — participant-specific and pod-wide — so a grant revoked mid-request no longer authorizes the mutation. Viewer credentials are read-only for lifecycle commands.

### Stable Occurrence Intake

Structured clusters publish through a first-writer-frozen occurrence store: versioned canonical JSON identity (JCS/SHA-256), the winner freezes the complete prepared aggregate, and contending workers adopt the persisted snapshot instead of racing to reshape it. Intake classifies new/recurrence/corroborating evidence per identity — active identities receive only unseen corroborating evidence and never a second investigation — and runs even while a triage Mission is already active, with the cluster's automation rules firing independently of Mission suppression.

### Immutable Automation Revisions + Fenced Inbox

`release.shipped` hands off to immutable rule revisions through a durable fenced inbox: per-generation deliveries with lease fences, per-action checkpoints that require a receipt to prove completion, a crash-atomic completion outbox, and proof-aware recovery. A stale lease resumes remaining actions only when a proved checkpoint demonstrates the admission guards passed; unprovable deliveries land in `attention_required` for explicit operator disposition (waive, or risk-acknowledged successor generation). The inbox is visible over REST with pagination, and disposition state races return 409.

### Release Activation Epochs

Each Release freezes one immutable activation epoch — cap, eligible Mission groups, exact Finding membership — and activation reconciles per-group under locked transactions with durable projections. Two reconcilers can never oversubscribe the cap or partially activate a shared Mission. Manual activation clears only the release gate on the EXISTING corrective Mission; release-mode activation retains it and attributes to the Release.

### Client Cutover + Strict Contracts

UI and MCP clients send lifecycle command intents only. Request schemas are strict (unknown fields rejected), `/promote` returns 404, the unlink patch shape returns a typed 400, and remote errors carry typed codes. `insert_deferred_mission` performs exactly one route request.

### Staged Enforcement

The one-shot production migration is replaced by a staged runner: the additive watermark (`0064`–`0067`) commits first, a versioned preflight with a database-local attestation gates enforcement, then the CHECK-guarded `0068` applies the partial-unique and RESTRICT invariants. Blocking anomalies (duplicate active identities, duplicate Finding Resolutions) defer enforcement with a stable code and a machine-readable report — startup never bricks; the server boots on the additive schema with service-level guards as the first line. Post-enforcement entries harden the chain further: the completion outbox and proved-receipt CHECK (`0069`–`0070`), and composite foreign keys that pin each evidence row to its Finding's habitat and each epoch group to its epoch's Release (`0073`–`0074`) — with rebuilds that archive any row the new keys cannot satisfy instead of dropping it.

### What Stayed the Same

Task lifecycle, workflow gates, plugin system, comments, and the remote participant actions from v0.35.0 are untouched. Cluster Resolution conversion, global Resolution uniqueness, and the legacy adapter window closure are deliberately out of scope.

### Schema Changes

Eleven migrations, `0064`–`0074` (see `docs/DATABASE.md`): additive lifecycle storage (provenance, lineage, activation, evidence, repair ledger), the occurrence store, automation revisions/inbox/checkpoints/outbox, release epochs and projections, the staged enforcement entry, and the post-enforcement hardening entries. No destructive column changes; every table rebuild preserves or archives existing rows.

### Operator Action Required

- **Update clients before upgrading:** stop using `/promote` (404) and the unlink PATCH shape (typed 400). Remote route callers must send an `Idempotency-Key`, hold `remote_contributor` standing, and use a `triage.route` grant scoped to the exact admitted Task. MCP must send `releaseGateVersion`. Handle 503+Retry-After and typed 409 codes.
- **Upgrade runs the staged migrations automatically** on next start. If boot reports `TRIAGE_ENFORCEMENT_PREFLIGHT_DIRTY`, the server is running safely on the additive schema; read the persisted anomaly report and remediate per the runbook in `docs/TROUBLESHOOTING.md` — enforcement retries on restart.
- **Provision `triage.route` grants** for remote contributors who route Findings (the shared scope catalog is the provisioning path).
- The automation inbox drain starts on boot — no external job required. Check `GET /habitats/:hid/automation-inbox` for `attention_required` deliveries after upgrade; disposition contracts are documented in `docs/API.md`.
