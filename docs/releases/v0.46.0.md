# v0.46.0 — Hardening: Mission Access Boundaries, Sprint Ownership, Dependency Integrity

v0.46.0 lands a verified-audit hardening batch: three independently reproduced defects are closed — unauthenticated-actor access to private Mission comment threads and template application, silent double-commit of a Mission into two Sprints, and the permanent dangling-row gap on Mission dependency edges — and the repository's lint and main test suite now run in CI on every pull request and main push, ending the local-gates-only verification posture. Every fix shipped with an executed reproduction that flipped to guarded under the fix, plus mutation-proven regression tests.

Before v0.46.0, the Mission comment routes and template application authenticated the caller but never checked membership in the target Mission's team habitat, so any authenticated local human could read private team comment threads and publish template Missions and Tasks into a private habitat — while the Mission detail routes 403'd the very same caller. A Mission could be committed to two planning Sprints at once, and cancelling or deleting the stale Sprint then destroyed the Mission's current Sprint pointer even though its live Sprint still listed it. Mission dependency edges carried no foreign key on the source side, so deleting a Mission that owned dependencies left dangling rows forever. And none of the repository's lint or main-suite gates ran in CI — the whole cycle was verified locally.

---

### The Mission Access Guard — Comments and Template Application

All four Mission comment handlers (`GET/POST/PATCH/DELETE /missions/:id/comments[...]`) and `POST /missions/:id/apply-template/:templateId` now carry the `requireMissionAccess` preHandler the Mission detail routes already use: the target Mission's actual Habitat is resolved server-side (a missing Mission or parent Habitat is 404), local agents keep their broad admission on any existing habitat, personal habitats stay open to any authenticated human, and team habitats require team membership — nonmembers, including global admins, receive 403 with no rows read, written, or disclosed. A real-HTTP wire matrix on both served prefixes pins the full admission table (anonymous, nonmember, member, local agent, personal-habitat human) including agent-authored writes, and denied writes leave zero rows.

### Sprint Single Ownership

A Mission is now owned by at most one non-terminal Sprint. Attaching one already held by another planning or active Sprint is rejected with `409 Mission is already committed to another sprint` (detach it first); a completed, cancelled, or deleted referenced Sprint leaves a stale pointer and re-attaching is allowed as the recovery; re-attaching to the same Sprint stays idempotent. Independently, every site that clears `missions.sprintId` — Sprint deletion, cancellation, and both completion carry-over paths — only clears pointers that name the detaching Sprint, mirroring the guarded update `removeMission` always had, so a legacy double-committed Mission keeps its live pointer when a stale Sprint that still lists it goes away.

### One Dependency Removal Contract

Mission dependency DELETE now speaks the same contract as the Task side, which the API documentation already described: an absent ordered pair is `404`, an existing pair is removed exactly once, and an unexpected database failure propagates as 5xx instead of collapsing into the not-found answer. The duplicated repository implementations are gone (the dependency module is the single owner), and the lifecycle test that previously pinned idempotent-success now pins the unified contract.

### mission_dependencies Source Foreign Key

Migration `0086` rebuilds `mission_dependencies` with the symmetric `ON DELETE CASCADE` foreign key on `mission_id` — the destination side always cascaded; the source side carried no key, which is how the dangling rows happened. The rebuild uses the established archive-then-mirror pattern: rows with a missing endpoint Mission are preserved in `mission_dependencies_orphans_0086` (normally empty; anything captured needs explicit remediation) and excluded from the mirrored copy, so no replacement key can abort the upgrade and nothing is silently dropped. Deleting a Mission now removes the dependency edges it owns, exactly as it already removed the edges pointing at it. The migration upgrade ledger fixture is now journal-tail-derived, so future migrations join the upgrade expectation without fixture edits.

### Continuous Integration for Lint and the Main Test Suite

A `lint-and-tests` workflow runs on every pull request and main push with the same conventions as the production-migration gate: oxlint over the workspace sources (errors fail, the known warning backlog is triaged separately), and the root test script — the scripts suite plus every workspace package's default vitest suite — after building `@orcy/shared`. Post-push verification for the solo workflow, not a required status check; local prevention stays in the pre-push hook.

### Release-Notes Backfill

The tracked operator notes for `v0.34.2`–`v0.34.5`, previously published only as GitHub release bodies, now exist in `docs/releases/` with verified commit links.

### What Stayed the Same

Agent admission policy (broad local-agent access is intentional), personal-habitat openness, the Mission detail and dependency boundary behavior, the plugin system, daemon, CLI, MCP surface, and all SSE event types. No new REST routes, MCP tools, or notification events. `0000_schema.sql` is untouched; migration `0086` is purely additive over the journal.

### Schema Changes

- **Rebuilt table:** `mission_dependencies` gains `FOREIGN KEY (mission_id) REFERENCES missions(id) ON DELETE CASCADE` (migration `0086`), symmetric with the existing `depends_on_id` cascade; orphans archive `mission_dependencies_orphans_0086`.

### Operator Action Required

**None for a clean upgrade.** Migration `0086` runs automatically on startup and normally archives nothing. If your database predates source-side integrity and the archive table is non-empty after the upgrade, those archived edges are historical dangling rows — review and delete them deliberately; the API no longer surfaces them.
