# v0.45.0 — Habitat Access Containment and Scheduled Occurrence Recovery

v0.45.0 closes a class of authorization gaps where a valid local human account that was **not a member of a private Team** could read or mutate that Team's data when object ids were known: mission detail, task, progress, and pulse reads; habitat listings; notification subscription writes; and the five Mission dependency endpoints now resolve the target object's actual Habitat and enforce the shared membership predicate before any read or write. Alongside the access work, the release restores scheduled-occurrence correctness — manual runs consume the occurrence they were issued for, committed reserved occurrences are recovered across restarts, and a durable occurrence-history table replaces unbounded re-derivation — and hardens the foundation: the declared dependency-resolution policy is now actually enforced by the pinned package manager, webhook failures are reported with their reasons, and the API test suite gained a shared compiled build that cut its wall-clock floor roughly in half.

Before v0.45, these admission checks authenticated the caller but stopped short of authorizing the target: mission-scoped reads and Mission dependency endpoints returned private-Team data to any authenticated human, habitat lists leaked team scoping to teamless users, and subscription writes were not bound to the URL Habitat. Scheduled tasks could consume the wrong occurrence on a manual run after an edit, silently lose committed reserved occurrences across a restart, and accept ambiguous or impossible calendar dates. The manifest declared dependency floors (`hono`, `postcss`, `esbuild`, `@hono/node-server`) in a field the pinned pnpm never reads, so the committed lockfile resolved below every floor. And the API test suite recompiled the package once per worker, bounding even a parallel run at several minutes.

---

### Habitat Access Containment

Mission detail, task, progress, and pulse reads now resolve the target Mission's actual Habitat (missing objects are `404`) and require Team membership for human callers — nonmembers, including global admins, receive `403` with no private metadata disclosed, while personal habitats admit any authenticated human and local agents keep their intentional broad admission. Habitat listings are scoped for users without teams, notification subscription writes are bound to the URL Habitat inside one immediate transaction (update and delete outcomes are now distinct), account state is isolated across authentication changes, and notifications for retired sessions are suppressed. MCP dispatch validates its keys and arguments before any client call, and malformed requirement entries are rejected outright.

### Mission Dependency Authorization and Conflict Semantics

The five Mission dependency operations (`GET/POST /missions/:missionId/dependencies`, `DELETE .../:depId`, `GET .../blocked-status`, `GET .../dependency-graph`) enforce the same membership predicate before any projection or write. Reads additionally authorize **every linked Mission** the response would disclose — both dependency directions from a raw both-direction inventory, each `blockedBy` Mission, and every traversed graph node — so an accessible root never leaks an inaccessible linked Mission's title, status, or node. Writes authorize only the selected ordered pair: a duplicate `POST` is `409 already_exists` (previously a `500`, because the composite primary key reports a different constraint code than the service caught) with exactly one edge row, and an absent `DELETE` pair is `404`. Dangling source-side edges (the source Mission deleted) carry no disclosable metadata and are skipped or dropped rather than failing the read; a persistent inventory/projection disagreement fails closed with `503`. Authorization is request-time only, matching the Task dependency boundary.

### Scheduled Occurrence Correctness and Recovery

A manual run of a scheduled task now consumes the occurrence it was issued for, even after schedule edits move the due pointer, and replay failures preserve their retry guidance instead of collapsing to a terminal view. Run outcomes are guarded against view-settlement races, and progress references report only real Mission rows. Committed-but-reserved occurrences are recovered at boot through a durable handoff, and a new occurrence-history table records each occurrence's admission and settlement evidence with bounded reads — the admission path no longer re-derives unbounded history. Offsetless ISO schedule dates are interpreted as UTC, impossible calendar dates are rejected, and one-time schedule edits align with their resume times.

### Delivery Monitoring and Webhook Integrity

The notification delivery monitor is actually populated (it previously stayed empty), recent-monitor reads are bounded and index-backed, and webhook diagnostics are size-bounded. Remote webhook HTTP failures are reported with their reasons and habitat targets preserved, delivery cancellation cleans up its worker state, and overdue deadlines are compared by instant rather than timestamp shape — pinned by a non-UTC timezone regression test.

### Content and Validation Hardening

Wiki drafts are preserved across independent saves, draft write settlements are reconciled, and acknowledgements survive older observations. Malformed scheduled task definitions fail isolated to their own task instead of poisoning shared state.

### Dependency Resolution Policy and Build/Test Throughput

The resolution policy moved from the npm-style top-level `overrides` field — which the pinned pnpm never read, leaving every declared floor silently unenforced — to `pnpm.overrides`, with the lockfile regenerated under the pin: single resolutions throughout (hono 4.13.13, @hono/node-server 1.19.17, postcss 8.5.13, esbuild 0.27.7) and compatibility verified by a full workspace build and every package test suite. A policy regression check now runs as part of the root `test` command and fails on any lockfile version violating a declared floor (with correct caret semantics for `0.x` floors). The API package's build no longer emits test sources, and the API test suite shares one compiled build across workers — with an opt-in `ORCY_TEST_TICK_MS` seam letting the boot-smoke tests run real 60-second worker ticks at 1.5 s, the parallel suite's wall clock drops to about 1 minute 43 seconds. The root lint baseline is green again, and the `prod` command builds first — a failed build starts neither service and exits nonzero — with both services then running in supervised process groups that shut down, escalate, and report status correctly on exit, interrupt, or terminal hangup.

### What Stayed the Same

The plugin runtime and its invocation contracts, the MCP tool registry surface, the task lifecycle and claimability model, and the sql.js/better-sqlite3 dual-backend portability model are unchanged. Authorization remains request-time admission (no membership-revocation or ABA fencing was introduced), local agents retain broad pod-wide admission by design, and the Learning Loop stays dormant behind its existing defaults. No API route was added or removed.

### Schema Changes

- `0084_scheduled_occurrence_history.sql` — new scheduled-occurrence history table recording per-occurrence admission and settlement evidence, replacing unbounded history re-derivation (additive).
- `0085_notification_monitor_query_indexes.sql` — covering indexes backing the notification delivery monitor's bounded recent-delivery reads (additive).

Both migrations are additive and applied by the staged production migration runner at boot.

### Operator Action Required

**None.** Both migrations are additive and apply automatically at next startup; the dependency floors are enforced by the lockfile at install time with no configuration change. `ORCY_TEST_TICK_MS` and the `ORCY_PROD_*` variables are test seams, not operator configuration — a boot that does not set them behaves exactly as before.

### Verification

Full API suite on the release commit: 564 test files, 9,340 tests green at default parallelism (single-worker serial verification also green on the release's largest change); shared, mcp, cli, ui, and installer suites green; workspace typecheck clean; root lint exits 0; a clean frozen install validates the regenerated lockfile; and the production-migration gate ran green in CI on every merged PR in this release, covering both new migrations.
