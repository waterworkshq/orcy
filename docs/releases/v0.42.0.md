# v0.42.0 — Task Transition Budget

v0.42.0 gives every task a **transition budget**: a per-habitat ceiling on how many times one task may cycle through its Execute↔Review loop before Orcy refuses further autonomous transitions and escalates to the habitat's humans. The meter is the task audit trail itself — no counter to drift, no new task status, no change to how any existing brake works — and the semantics are recorded in ADR-0051. The ceiling design came out of a public design discussion on r/softwarearchitecture; the per-task scope and finite-by-default semantics were proposed by **donk8r**, and this release ships with their name on it, as promised in the thread.

Before v0.42.0, nothing bounded the aggregate review loop. The retry ladder capped retries within a policy, and recovery caps bounded spawned recovery tasks — but a task could bounce claim → start → submit → reject → re-claim indefinitely, and per-session agent spend caps reset on every invocation, so ten review rounds cost ten times any per-invocation cap. A misbehaving loop could run forever, burning agent spend the whole way down.

---

### The Brake and the Meter

The budget meters the audit trail: every task event in the review cycle (`claimed`, `started`, `submitted`, `rejected`, `released`, `failed`, `retry_scheduled`, `retry_executed`) counts toward the ceiling. Convergence exits (`approved`, `completed`) and bookkeeping actions (`created`, `updated`, `deleted`, `delegated`) are untaxed — finishing a task never consumes budget, and neither does editing it. **Human actors are never metered**: the brake exists to stop autonomous spend, and the human who steps in to resolve a stuck task is never blocked by it. When the count reaches the ceiling, the next metered attempt is refused with an explicit reason (`transition_budget_exhausted` on the claim path, a typed budget error on submit) carrying the count and the ceiling, so callers and logs can tell exhaustion apart from ordinary contention.

### The Setting and the Arithmetic

The ceiling is a new habitat setting, `lifecycleSettings.taskTransitionCeiling` (PATCH `/habitats/:id`, same deep-merge semantics as the other habitat settings blobs): `null`/unset → the default, `0` → an explicit opt-out (the habitat is unmetered), or a positive integer up to 10,000. The **default is 21**, and the honest arithmetic behind it: a first pass costs 3 transitions (claim + start + submit), and each fix round costs 6 with a retry policy in force (reject, retry scheduled, retry executed, re-claim, re-start, submit) or 4 without. So 21 buys the first pass plus three complete policy-driven fix rounds — or four rounds without a policy — matching the design intent of "three or four fix rounds" in both regimes. An earlier planning sketch of 12 assumed ~3 per round; the review-corrected math raised the default rather than silently shortchanging the loop.

### Breach: Refusal and Escalation

At the (N+1)th metered attempt the transition is refused — the task stays in its current status; the budget never invents a new one. The first breach escalates to the habitat's humans: the existing `escalated` task event (visible in the audit trail and over SSE) plus an in-app notification carrying the count, the ceiling, the refused action, and both remedies — raise the ceiling or resolve the task as a human. Repeat attempts keep refusing but do not re-notify. The escalation is deliberately scoped so it can never collide with the retry ladder's own escalation events. Two known edges, documented in ADR-0051: if the ceiling is raised after a breach and the task later breaches again, no second notification fires (the task simply stops progressing — watch for that); and remote participants see a generic submit/release failure on the shared API surface (the typed budget diagnostics exist on the internal wrapper returns, but the remote wire intentionally stays terse as an anti-probing measure).

### What Stayed the Same

The retry ladder still governs backoff and per-retry escalation; recovery-spawn depth caps are untouched; approval and completion paths are untouched; no route contracts changed shape (the only wire additions are the new typed refusal reason and budget diagnostics fields); opted-out (`0`) habitats behave exactly as before. The full API suite passes unchanged apart from the budget's own discriminators. This release window also carries one test-infrastructure hardening — isolated per-invocation temp ownership for the staged-enforcement suite, so two overlapping test runs can no longer destroy each other's databases — with no runtime surface.

### Schema Changes

One additive column: `habitats.lifecycle_settings` (migration 0075, a nullable JSON blob). No other tables, no data migration.

### Operator Action Required

**None.** No migration to run by hand, no configuration to set, and installers need no change. One behavior change to be aware of: habitats that never configure the setting get the finite default of 21 — cycles that previously ran unbounded will now escalate. That is the deliberate backstop. If a legitimate long-cycle workflow trips it, raise `lifecycleSettings.taskTransitionCeiling` for that habitat (or set `0` to opt out entirely), or resolve the task as a human — human actions are always unmetered.
