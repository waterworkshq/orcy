# v0.34.0 — Deepen: Workflow Gate Advancement

v0.34 is an architecture-deepening release that concentrates the Workflow Gate advancement transaction into one deep module behind a single `advanceGates(decisions, trigger) → AdvancementResult[]` entry point. Per-gate `db.transaction` owns guarded CAS satisfaction, tx-aware audit INSERT, and recovery handoff for eligible `on_fail` gates. Five satisfaction paths — lifecycle transitions, Pulse Signals, Automation Run completions, manual unblocks, and recovery redemption — route through the one entry. A sixth path (template pre-satisfied-at-attach) is a creation-time exception. ADR-0042 documents the fail-closed atomicity contract.

Before v0.34, gate satisfaction, audit emission, `satisfiedByEventId` stamping, error classification, and recovery spawning were distributed across three trigger handlers (`handleTransition`, `handlePulseCreated`, `handleAutomationRunCompleted`), a redemption bypass (`redeemOneContext` that direct-wrote gates with no audit), and a manual-unblock path (`manualUnblockGate` that used a separate store mutation with a different audit action). The v0.26 extraction (`WorkflowGateEvaluator` + `WorkflowGateStore`) had improved organization but left the semantic transaction distributed: callers still owned commit ordering, audit metadata, idempotency reasoning, and error policy. The audit helper (`emitWorkflowTaskAudit`) swallowed write failures after satisfaction had already committed — hiding code bugs as silently-satisfied-no-audit gates. And the recovery spawn path (`spawnRecoveryForGate` → `createRecoveryTask`) collapsed every non-successful publication outcome to `return null`, stranding satisfied `on_fail` gates with `recoveryTaskId = null` forever — a reachable production bug, not a theoretical crash window.

---

### The Advancement Transaction

The new `WorkflowGateAdvancer` module (`workflowGateAdvancer.ts`) owns one `db.transaction` per satisfiable decision. Each transaction performs three writes: a guarded CAS satisfaction UPDATE (SELECT-before-UPDATE discriminator classifies `satisfied` vs `already_satisfied`; the `WHERE satisfied = false` guard is preserved as defense-in-depth), a tx-aware audit INSERT via a new `createEventWithClient(db, input)` primitive (failures propagate, never swallowed), and — for eligible `on_fail` gates only — a recovery handoff row INSERT into the new `task_recovery_handoffs` table. An audit failure or handoff failure rolls back all three writes. This is a fail-closed contract: a gate does not advance unless its required provenance (and, where applicable, recovery expectation) commits with it.

The contract is deliberately NOT eventual delivery. Source hooks are one-shot: `notifyTransition` swallows hook errors, the lifecycle event commits before the hook fires, and pulse and automation-run completion have no redelivery path. There is no outbox, no advancement-attempt ledger, no automatic replay. A gate can remain unsatisfied until operator intervention or a genuinely new matching trigger. ADR-0042 makes no eventual-liveness guarantee.

Transactions are per-gate, not batched — one gate's audit failure does not block later independent gates (verified by the preserved per-gate error isolation test at `workflowAuditEvents.test.ts:368-405`).

### Six-Way `satisfiedByEventId` Normalization

The `satisfiedByEventId` column — rendered by the UI (`WorkflowGatePanel.tsx:104`) as the causal provenance source — was populated for only two of six satisfaction paths. Four of six rendered *nothing*. The deepening normalizes all six:

| Path | Before | After |
|---|---|---|
| Lifecycle | NULL | Real Task Event id (forwarded via new `transition-emitter.ts` seam) |
| Pulse | `pulse.id` | `pulse.id` (unchanged) |
| Automation | `run.id` | `run.id` (unchanged) |
| Manual unblock | NULL | Self-referential audit id (caller preallocates; `result.triggerEventId === audit.id === gate.satisfiedByEventId`) |
| Redemption | NULL (no audit at all) | Recovery context id (per-gate `workflow_gate_satisfied` audit emitted) |
| Template pre-satisfied-at-attach | Synthetic `pre_satisfied_at_attach:${now}` | Unchanged (namespaced synthetic exception, distinctly UI-labeled) |

The lifecycle normalization required a hidden seam change in `transition-emitter.ts`: `emitTransition` now captures the persisted Task Event id (previously discarded) and forwards it through `notifyTransition` as an optional `eventId?` field. The field is optional because `notifyTransition` fires for ALL actions including `deleted` (which creates no Task Event); the `GateTrigger.lifecycle` kind requires it (enforced adapter-side — the five gate-mapped actions all produce events). A second `notifyTransition` producer in `taskCreationDispatchAdapters.ts` forwards `envelope.eventId` for the `created` action. This preserves ADR-0005's two-channel subscriber contract (additive optional field; existing consumers ignore it by default).

### Audit-Action Map

The module emits a complete, asymmetric audit vocabulary:

| Trigger kind | `satisfied` | `already_satisfied` | Evaluator throw | Write failure |
|---|---|---|---|---|
| Lifecycle, pulse, automation, redemption | `workflow_gate_satisfied` | **No audit** | `workflow_evaluation_error` | Rollback |
| Manual unblock | `workflow_gate_unblocked` | `workflow_gate_unblocked` (CR-13/TG-1 attempt audit) | `workflow_evaluation_error` | Rollback |

Manual unblock is the ONLY trigger kind that emits an audit on `already_satisfied` — the CR-13/TG-1 carveout pins repeat-unblock behavior (second unblock emits a fresh `workflow_gate_unblocked` with an `already_satisfied` marker, never mutates the gate, never overwrites the original `satisfiedByEventId`). The other four kinds emit NO audit on `already_satisfied` (preserving the legacy `continue` behavior).

### Redemption + Manual Unblock Absorbed

`redeemOneContext` previously direct-wrote gates via `db.update(taskWorkflowGates)` with NO `workflow_gate_satisfied` audit — only a `workflow.recovery_succeeded` notification carrying a *count*, not gate ids. It now routes through `advanceGates` with a `recovery_redemption` trigger; each redeemed gate gets a per-gate audit + `satisfiedByEventId` stamp. The notification stays as UX. ADR-0035 defines notifications as operational current-state rows, not append-only mutation history — two records, two roles. The stale comment claiming "audit via the notification-to-audit projection" (the conflation defect) is removed.

`manualUnblockGate` previously called a separate store mutation (`satisfyManualGateIfEligible`) and emitted a different audit action. It now routes through `advanceGates` with a `manual` trigger. The module emits `workflow_gate_unblocked` (NOT `workflow_gate_satisfied`) for this kind — the distinct action is the provenance distinction, preserved. `satisfyManualGateIfEligible` is removed (dead code, zero callers). The `on_manual`-type eligibility check moves to the manual-unblock adapter.

### Recovery Coordinator

The old `spawnRecoveryForGate`/`createRecoveryTask` live-config path is removed entirely (−205 lines from `workflowService.ts`). A new `task_recovery_handoffs` table (migration `0060`) records durable recovery intent atomically in the advancement transaction. A boot-only `RecoveryCoordinator` consumes handoff rows joined to `task_creation_attempts` (the existing 8-state attempt ledger):

| Handoff | Attempt state | Action |
|---|---|---|
| `expected` + no attempt | — | Spawn: call `publishRecoveryTask` with frozen handler config |
| `expected` + `pending` | — | Retry: re-invoke `publishRecoveryTask` under same key |
| `expected` + `published_pending_*` | — | Resume: leave for existing publication workers |
| `expected` + terminal-success | `created`/`created_unassigned` | Consume: flip to `consumed` |
| `expected` + terminal-refusal | `vetoed`/`rejected_validation`/`batch_rejected`/`rejected_fingerprint` | Block: flip to `blocked` + operator-visible audit |
| Absent | — | Not-expected: noop |

The coordinator is boot-only — invoked immediately by the lifecycle adapter after `advanceGates`, once at boot, and on-demand for operators/tests. No periodic timer. The handoff freezes the resolved handler config at advancement time (Fork B: immutable payload); the coordinator uses `frozen_handler_config` from the handoff row and never re-resolves live `resolveEffectiveFailureHandler`. A restart honors the policy in force at advancement time, not silently adopted changed configuration.

The durable handoff is justified by the reachable null-collapse bug — not the unreachable process-kill crash window. Skeptical's YAGNI risk-acceptance is documented in ADR-0042: boot-only is the proportionality bound; revisit if incidents materialize.

### Debate + Review Process

The five load-bearing decisions were settled through a five-seat Traycer debate (Architecture, Reliability, Audit/Provenance, Skeptical, Testing) with models on `codex`/`gpt-5.6-sol` and `opencode`/`zai-coding-plan:glm-5.2`. The debate surfaced two corrections that reshaped the design: (1) the "trigger re-fires on retry" claim (justifying atomicity via redelivery) was refuted three ways and withdrawn — the honest justification is the fail-closed trade-off, not eventual liveness; (2) the dossier's three-way provenance asymmetry was upgraded to six-way with a user-visible UI hole.

The deep module (WG-3) received a dual independent review (`gpt-5.6-luna`/max + `gpt-5.6-sol`/high) that caught a Product Misalignment: the manual `eventId` preallocation was ignored (module minted a fresh audit id instead of using the caller-supplied `trigger.eventId`). The coordinator (WG-4) received an independent review (`gpt-5.6-sol`/high) that found two Major Drift items: `pending` attempts were stranded (no worker scans them) and both recovery notifications were dropped. All findings were fixed in fixup passes before commit. A final cohesive changeset review (`gpt-5.6-sol`/high) found three items (spurious unrecoverable notification when handler disabled, documentation drift, import cycle) — all fixed.

### What Stayed the Same

No new REST routes, MCP tools, SSE event types, or UI features. The `WorkflowGateEvaluator` match logic (signal/automation matching, condition evaluation) is unchanged. The `WorkflowGateStore` query methods (`findActiveLifecycleGates`/`findActiveSignalGates`/`findActiveAutomationGates`) remain thin query helpers. ADR-0005's two-channel subscriber contract is preserved (additive optional `eventId?`). ADR-0038 (claimability authority), ADR-0039 (plugin invocation), ADR-0040 (React Query sole authority) are respected throughout. The plugin system, daemon, CLI, and installer are untouched.

### Fork Resolutions

**Fork A (audit id acquisition):** caller-supplied preallocated IDs. sql.js `.run()` returns boolean `true` (not `{changes:N}` or `lastInsertRowid`) — empirically verified against `drizzle-orm@0.45.2` + `sql.js@1.14.1`. The manual-unblock adapter mints the audit-event id via `crypto.randomUUID()` and passes it as `trigger.eventId`; the module uses that same id for the audit INSERT and the self-referential `satisfiedByEventId` update.

**Fork B (handler-identity freeze):** immutable frozen handler payload. The coordinator uses `frozen_handler_config` from the handoff row, never re-resolves live configuration. A restart must honor the policy in force at advancement time.

### Schema Changes

- **New table:** `task_recovery_handoffs` (migration `0060`). Columns: `id`, `gate_id` (FK CASCADE), `workflow_id`, `habitat_id`, `mission_id`, `downstream_task_id`, `recovery_depth`, `trigger_event_id`, `frozen_handler_config` (JSON), `handler_fingerprint`, `status` (`expected | consumed | blocked` — no `spawned` state), `blocked_reason`, `created_at`, `consumed_at`. Indexes on `gate_id` and `status`.

### Operator Action Required

**None.** No manual migration step. No configuration changes. No breaking changes to REST/MCP/SSE contracts. The `transition-emitter.ts` seam change is additive (optional `eventId?` on `TransitionHook`).
