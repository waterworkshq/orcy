# v0.41.2 — Patch: Plugin handler-map ownership and hook installation observability

Two plugin-surface changes: plugin handler maps must actually own their declared entries before those entries validate or register, and the application's per-construction record of installed hooks now truthfully includes the hooks installed under the plugin route namespaces. No plugin manifest schema, route inventory, authentication policy, rate-limiting, or deprecation-header behavior changes ship in this patch.

## Plugin handler maps require owned entries

A plugin declares contribution ids — a channel id, detector id, interceptor id, tool name, formatter id, condition id, action id, or provider name — and the loader resolves each id against the corresponding map exported by the plugin module. That resolution used plain property access, which walks the prototype chain: a contribution naming `constructor` or `toString` against an otherwise empty handler map could validate and register an inherited Object.prototype function as its handler, and a provider contribution could likewise resolve an inherited object. Validation and registration now resolve a declared id only to a property the plugin's own handler map contains. Every legacy family — notification channels, signal detectors, lifecycle interceptors, custom MCP tools, webhook formatters, automation conditions, automation actions, and integration providers — rejects an inherited entry with its existing missing-handler error at load time, while correctly shaped own entries continue to load exactly as before. A plugin rejected this way is skipped without affecting other plugins discovered in the same pass, as before. Error messages, registry keys, collision handling, priorities, and provider method requirements are unchanged. Custom HTTP route contributions keep their existing stricter declaration-and-handler exact-agreement validation, which is untouched.

This is a behavior change, but only for the degenerate inherited-entry case: real plugins whose maps own their handlers load and register identically to v0.41.1.

## Hook installation observation now includes the plugin namespaces

When the application assembles, it records each hook it installs, per construction, as an ordered observation stream internal to the assembly. That stream previously reported the seven core hooks but omitted the three hooks installed when plugin routes are mounted: the per-agent rate-limit `preHandler` on the current plugin prefix, the same `preHandler` on the deprecated plugin prefix, and the deprecation-header `onSend` on the deprecated plugin prefix. The stream now appends exactly those three records, each emitted at the statement that installs its hook. This is an observability-only change: the hooks themselves are not new, reordered, or altered, no records are emitted when no plugins are loaded, and requests are routed, authenticated, rate-limited, and deprecation-stamped exactly as in v0.41.1.

- Mutation coverage: each load-bearing check added in this patch was bypassed one at a time and the intended tests failed while their neighbors stayed green. Restoring prototype-chain lookup turns exactly the fifteen inherited-entry rejection tests red while all eight own-entry control tests stay green; withholding one observation record while keeping its hook fails the hook-stream proofs while every behavioral probe stays green; and withholding an actual plugin hook while keeping its record fails the behavioral deprecation-header probes while the stream assertions stay green. The inherited-entry and hook-stream coverage is new in this patch; the suite totals above include all pre-existing coverage.

## No operator action required

No schema, migration, or configuration changes; no plugin manifest schema change and no change to the contract for handler maps that own their declared entries — the inherited-entry rejection described above is the only acceptance change, and no route, authentication, rate-limiting, or deprecation behavior changed. Plugins that already export handler maps owning their entries are unaffected; nothing to do on upgrade.
